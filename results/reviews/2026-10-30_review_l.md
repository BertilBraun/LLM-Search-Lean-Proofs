## Answer to the main question: with all options off, the live loop is unchanged

I checked each point the brief listed. I found nothing that changes training data, records or pause behaviour in a way
that matters.

### Grouping, prompts, credit and advantages: unchanged

- **Groups.** With the options off, every edge has `feedback = False` and an empty `name_repairs`.
  - In `policy_groups` (`grpo_groups.py:229-249`), `by_prompt[False]` therefore receives exactly the old `by_text`, in
    the same order, and `by_prompt[True]` stays empty and is skipped.
  - The groups, their sample order, their multiplicities and `require_policy_proof` all match master.
  - `group_advantages` is computed per group, so the advantages are identical.
- **Prompts.** `texts_by_prompt[(node_id, False)]` (`policy_data.py:230-236`) finds the same `ExpansionTexts` that
  `texts_by_node[node_id]` found:
  - Old records read `ExpansionTexts.feedback` as False by default.
  - With the options off, a node has exactly one `ExpansionTexts`. The batches abandoned under overlap are charged but
    never recorded as texts.
- **Held-out metrics.** `sample_success` (`single_step.py:209-218`) returns the same numbers, since no edge is
  repaired. `tree_summary.valid_blocks` is unchanged for the same reason.
- **Held-out run config.** `single_step_run_config` gives the old config when `failed_automation_in_prompt` is False:
  harvest off, kind `policy`, overlap off.

### Tree records

- **Old records still read.** Every new field has a default: `Edge.feedback`, `Edge.name_repairs`,
  `ExpansionTexts.feedback` and `PolicyStatistics.feedback_requests`.
- **New records work with the new readers.** The trainer, `tree_summary`, `graph_labels`/`tree_statistics` and the
  resident trainer read them fine. The dashboard reads raw JSON series (`monitoring/store.py`), so it is unaffected.
- **Caveat.** Master's strict reader cannot read the new records. See finding 8 (rollback only).

### Pause gate

The new `GatedExpander` (`loop_search.py:93-104`) enters the gate once per `anext`, including a final `anext` that
only finds the inner generator exhausted.

- **Can a pause miss a request?** No. `pause()` waits only for `in_flight == 0`, and every request runs between an
  `enter` and a `leave`:
  - `enter` is atomic: `Event.wait` on a set event does not suspend.
  - A cancellation inside `enter` never incremented the counter.
  - A cancellation inside `anext` runs the `finally: leave`.
- **Can it deadlock?** No. A search blocked in `enter` is not in flight, so it cannot hold the pause.
- **The one behavioural difference.**
  - A search whose last batch finished during a pause now waits at the gate until the resume.
  - Before, it went on to `_enqueue`. That blocks at the gated value request anyway when there are children. With no
    children to score, it went on to the next pop, and under overlap the next node's automation sweep ran during the
    pause.
  - The new behaviour is harmless. If anything it is better, because the paused searches' REPLs are stopped for
    training.
- **Version labels.** `policy_version` is read right after `enter`, as before, so samples carry the same labels.

### Overlap

- `CompositeExpander` (`expanders.py:142-174`) now prefetches only the first batch of each later expander.
- In the live config (`automation_then_policy`, `overlap = true`), both the automation expander and the policy
  expander yield exactly one batch when the options are off. Request timing and abandoned-batch charging are therefore
  identical.
- The new `finally` gathers the prefetches and then closes the generators. I traced these paths:
  - normal completion;
  - GeneratorExit after a proof;
  - GeneratorExit while the task is being cancelled;
  - CancelledError while awaiting the current generator directly.

  None of them leaves a running generator or misses a `gate.leave`.
- Nothing here slows sampling.

### `search_states`

- It now cancels the other searches when one fails, before the pool closes.
- This is an improvement, and it changes nothing on success.

## Findings, by severity

None of the findings below affects the live loop with the options off. Findings 1-7 matter only for the harness, or
once an option is turned on. Finding 8 matters only for a rollback.

### 1. (Medium) The harness's version guard misses the window between the servers' wake and the version's record

**Where.** `experiments/search_variants.py:115-120` (`ensure_version`, which reads `read_current(...).version`), and
`rl/loop.py:1316-1354` (`publish`) with `loop.py:1356-1370` (`record_durably`).

**Scenario.**
- The live loop runs with `training.persistent = true`, which is the handoff path.
- In that path, `publish` wakes or swaps every server to version k+1 and resumes the searches.
- Only later does `record_durably` copy the merges to disk (roughly 14 GB) and write `current`. Until then
  `read_current()` still returns k.
- Harness requests that the server held during the pause (`/pause?mode=wait` queues new requests) are answered by
  k+1 as soon as the server resumes. This happens if the pause is under the 900 s request timeout; the README
  estimates 10-15 min per pause.
- Requests sent right after the resume are also answered by k+1.
- These single-step trees finish within seconds, long before the durable write ends. So `ensure_version()` passes,
  and trees sampled by k+1 are written under `v<k>/`.
- The same happens if the harness is started inside that window: its whole directory is labelled k while k+1 serves.

**Effect.** The paired comparison mixes two policy versions, both within one variant and across variants. That
defeats the stated purpose: "every variant of one invocation must see the same one".

**Fix.** Guard on something the loop changes at the pause itself, not at the record:
- Read the loop's `progress.json` phase (or a `served.json` that the loop writes in `searcher.serving`) at the
  start of each state's search and again before writing it. Discard the tree if either value changed or if the loop
  status is not `searching`.
- Also refuse to start while the loop is in the publishing stage with the record not yet written.

**Confidence.** Medium-high. I read the ordering in the code; I did not run it.

### 2. (Medium) The headline "Δ success vs baseline" is biased against the feedback and combined variants

**Where.** `rl/search_variants.py:370-371` (`pooled_rate`) and `:389-411`. The value feeds the first data column of
`comparison_table`.

**Scenario.**
- The pooled rate is total successes over total samples.
- The feedback round adds 4 samples only at states whose first round reached fewer than 2 new states. Those are
  mostly hard states with low success.
- So the feedback variant's extra samples weight the pool toward hard states. Its pooled rate can fall even when it is
  strictly better.
- The reproduction shows this:
  - The first rounds are identical: an easy state at 8/8 and a hard state at 0/8.
  - The feedback round solves 1 of 4 on the hard state.
  - The variant's pooled rate is 9/20 = 0.45 against the baseline's 8/16 = 0.50, so Δ = -0.05.
- The bootstrap interval inherits the same bias.

**Effect.** The comparison could reject the feedback option even though it helps.

**Fix.** For variants that add samples, compare per-state quantities instead:
- the mean over states of the per-state success rate;
- `states_with_success`;
- successes per generated token.

Keep `first_round_success_rate` as the sanity check. It should not differ from the baseline beyond noise, because the
first round's prompt is the same.

**Confidence.** High (reproduced).

### 3. (Low-Medium) With harvesting on, the feedback round runs after the node already found a proof, and its tokens are charged to `solved_at`

**Where.** `policy/expander.py:243-262` together with `search/search.py:320-334` (`_Expansion.stopped`, where
`finish_after_proof` is set from `harvest.enabled`).

**Scenario.**
- Harvesting is enabled in the live search config (`visible_student_v2.toml [search.harvest] enabled = true`). It is
  also enabled in the harness's `tried_context` and `combined` variants (`single_step_run_config`: enabled, 0
  expansions).
- In those configs, an expansion that finds a proof keeps going, and the search asks the expander for its next batch.
- The proof child counts as one `CHILD`. If the other samples failed, the count is below `min_children = 2`, so the
  feedback request is sent at a node that is already solved.
- Because `expansion.solved` is True, the request's tokens go to `solved_at` too, which inflates the cost to the first
  proof.
- The reproduction shows this: 2 requests instead of 1, and `solved_at.generated_tokens` rises from 2 to 4.

**Fix.** Skip the round when the node has a proved child. Two ways:
- check `any(edge.target_id is not None and tree.node(edge.target_id).is_proved for edge in edges)`;
- or expose `expansion.proved` through `SearchContext`.

**Confidence.** High (reproduced).

### 4. (Medium, measurement validity) `tried_context` changes more than the prompt in the 120 s held-out cap

**Where.** `rl/single_step.py:114-135`, `search/search.py:536-546` (the wall check before each candidate) and
`rl/search_variants.py:223-251`.

**Scenario.** The variant now runs the full sweep at the root before the policy request: 7 tactics, 200k heartbeats
each, the 60 s emergency stop, and no overlap.
- **Lean cost.** Every state pays the whole sweep serially before the request is sent. The sweep's wall-clock
  timeouts also restart a REPL process. On slow states the sweep can use most or all of `max_wall_seconds = 120`.
- **Lost samples.**
  - If the time runs out during the sweep, the expansion stops and the policy request is never sent.
  - If it runs out partway through the candidates, the remaining candidates are never recorded.
  - In both cases those samples disappear from the denominator; they are not counted as failures.
  - Slow states tend to be hard ones, so this raises the variant's pooled rate.
- **Fewer children.** States the sweep already reached make the policy's samples there `DUPLICATE` instead of
  `CHILD`.
  - This lowers `children` and `states_below_two_children` for `tried_context` and `combined`. Success itself is not
    affected, because it is judged by goals.
  - In `combined` it also triggers more feedback rounds.

**Fix.**
- Record the sweep's wall time apart, or give the sweep its own budget outside the 120 s.
- Count samples that were requested but never run as failures, or report them.
- Count states reached by the policy whether or not the sweep reached them first, i.e. by goal key, not by edge
  outcome.

**Confidence.** Medium. This is from reading the code; no Lean run.

### 5. (Medium, operational) By default the harness doubles the node's Lean processes beside the live loop, and the loop knows nothing of it

**Where.** `experiments/search_variants.py:126-129`. The default concurrency is the held-out target's 112
(`loop.toml [evaluation.held_out_states] concurrency = 112`).

**Scenario.**
- The loop's own held-out evaluation runs 112 REPLs only at the pause, after the paused searches' REPLs have stopped.
- Its evaluations beside sampling cut sampling to at least 56 searches.
- The harness, started "beside the running loop", adds 112 REPLs on top of the loop's 112 searching REPLs. This is
  outside the host-memory budget in `rl/README.md` "Host memory". The CPU is shared, so the loop's Lean-bound searches
  slow down.
- At the next pause:
  - The servers' `/pause?mode=wait` drains the harness's requests as well.
  - The harness's later requests queue for the whole training phase, then time out. Its run aborts and must be
    resumed.
  - Requests that do not time out cause finding 1.

**Fix.**
- Default `--concurrency` to something small, for example 16-28.
- Document that the harness should run while the loop is stopped, or at a known lull.
- Or teach the loop to count it like an evaluation beside sampling.

**Confidence.** Medium. The memory and CPU impact depends on REPL p90 memory.

### 6. (Low) Running in chunks (`--first-state/--states`) overwrites earlier chunks' results

**Where.** `experiments/search_variants.py:135-140`.

**Scenario.**
- `state_results(states, records)` covers only the current invocation's states. `states.jsonl` and `summary.json`
  are then overwritten with them.
- A second chunk run into the same variant directory replaces the first chunk's rows.
- `compare` reads only `states.jsonl`. The first chunk's trees stay on disk but drop out of the comparison.
- Meanwhile `run_wall_seconds` keeps accumulating over both chunks.

**Fix.** Merge `states.jsonl` by state name, or rebuild the results from every tree in `trees/`.

**Confidence.** High.

### 7. (Low) The feedback prompt can show text the policy did not write, and blocks that made progress

**Where.** `policy/expander.py:204-219` (`failed_attempts` / `failed_attempt`).

**Scenario.**
- **Repaired blocks.** With `name_repair` on, the failed attempt shows `edge.text`. That is the repaired block, with
  the error from the repaired run, so the policy is told it wrote something it did not.
- **Partly applied blocks.** A block that applied some tactics and then failed is recorded as `CHILD` (or `DUPLICATE`)
  with a `failure`. It counts toward `min_children` and is also listed under "These attempts failed here".

**Fix.**
- Skip repaired edges, or keep the sampled text and error on the edge.
- Restrict attempts to edges with `outcome in (FAILED, REJECTED)`.

**Confidence.** High that the code does this; low impact.

### 8. (Low, rollback only) Master cannot read records written by this commit

**Where.** `search/records.py:171-173` rejects unknown keys. `dataclasses.asdict` always writes `feedback` and
`name_repairs` on every edge and `feedback` on every `ExpansionTexts`, even with the options off.

**Scenario.**
- Deploy this commit, then roll the loop back to master for any reason.
- Every tree written in between then fails to read:
  - the value window's trees (4 phases);
  - the `TreeStore` phase entries;
  - the resident trainer's reads.

  The error is `Edge: unknown keys ['feedback', 'name_repairs']` (reproduced).
- The same applies to `run_config.toml` written by `run_config_text`, which now carries `[policy.feedback]` and
  `[search.name_repair]`.
- Earlier field additions (`tactic_goals`, `policy_version`) had the same property, so this follows an accepted
  pattern.

**Fix.** Either of:
- merge this commit to master before the restart and treat it as a one-way change;
- omit default-valued new fields when writing.

**Confidence.** High.

### 9. (Low, performance with `name_repair` on) Repair work blocks the event loop

**Where.** `lean/identifiers.py:616` (`@functools.cache namespace_members`) and `:648` (`difflib.get_close_matches`).

**Scenario.**
- `namespace_members` runs through `asyncio.to_thread` at every search's start. The cache has no lock, so when 112
  searches start together, up to 32 executor threads each build the full namespace map (about 200k constants) under
  the GIL.
- `get_close_matches` runs synchronously on the event loop. It scans namespaces such as `Nat` or `Finset`, which have
  thousands of members, for every unknown name.

**Fix.**
- Build `namespace_members` once, under the `environment_names` lock (next to `_loaded_names`).
- Run the repair in `asyncio.to_thread`, or pre-bucket each namespace's members by length or first character.

**Confidence.** Medium on the magnitude, which I did not measure.

## Checked with the options on, and correct

- **Feedback groups get their own prompt and advantages.**
  - The edges' `feedback` flag comes from the batch's flag, and `ExpansionTexts.feedback` comes from the same batch.
  - `policy_data` looks up `(node_id, feedback)`.
  - `group_advantages` is computed per group.
  - A feedback sample that repeats a first-round block is `REPEATED`. It sits in the feedback group, with the
    first-round edge's tactics as its executed tactics.
  - Each `ExpansionTexts` carries its own `policy_version`, so a pause between the two rounds labels each round
    correctly.
- **Edge cases.**
  - No failed samples, all `DUPLICATE`, or all `UNPARSED`: `failed_attempts` is empty, so no round.
  - Proof in the first round with harvesting off: the generator is closed, so no round.
  - Feedback prompt too long: `None`, so no batch.
  - With harvesting on, see finding 3.
- **Masking of repaired samples covers every token-training path.**
  - `policy_groups` tests `record.edges[edge.executed_edge_id].repaired`. That also excludes later samples with the
    same original text: they are `REPEATED` with `repeat_of` the repaired edge, because `edge_id_by_text` is keyed by
    the sampled text.
  - A genuine sample that writes the corrected name runs as its own edge and stays trainable.
  - `sample_success` and `tree_summary.valid_blocks` exclude repaired samples.
  - Proof steps and value states built from repaired edges are Lean-checked, so they are fine to keep.
  - The harness deliberately counts repaired successes. Its docstring says so, but this differs from the loop's
    held-out metric.
- **The harness's paired bootstrap mechanics are correct.** It resamples states with pairs and uses the right
  quantile indices. The problem is the statistic, finding 2.

## Verdict

**Safe to deploy to the live loop with every option off.** With the options off:
- training groups, prompts, credit and advantages are identical to master's;
- records stay readable by the new code;
- the pause gate cannot miss a request or deadlock;
- overlap timing is unchanged.

The only operational caveat is finding 8: after the restart, do not roll back to master without a reader that tolerates
the new keys.

**Do not use the harness's headline numbers to decide on enabling options** until findings 1, 2 and 4 are fixed. Do
not run it at its default 112-REPL concurrency beside the live loop (finding 5). Before `policy.feedback` is enabled
in the loop, fix finding 3.
