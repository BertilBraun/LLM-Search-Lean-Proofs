## Findings, by severity

### 1. A server failure during an evaluation beside sampling stops the whole loop instead of being recovered (high)

**Where:**

- `src/lean_search/rl/loop.py:1366-1372`: `start_evaluations_beside_sampling` wraps the task in `stopping_on_failure`.
- `loop.py:1378-1389`: `evaluate_beside_sampling`.
- `loop.py:852-884`: `recover_servers`, including its new docstring.
- `src/lean_search/rl/evaluation.py:470-487`: `search_problem_set` has no handling for HTTP errors.
- `src/lean_search/rl/loop_services.py:246-247`: `run_logged` raises on a nonzero exit.

**Scenario:**

1. A vLLM server dies, or stalls under load, while the probe or miniF2F runs beside sampling. Under the shipped
   schedule that window covers a large share of sampling time: a probe slot every 2 h, plus hours at the start.
2. The evaluation job's searches get `httpx` errors. The policy client retries a little and the value estimator retries
   transport errors, but neither survives a dead server. `asyncio.gather` in `search_problem_set` propagates the error
   and `grpo_evaluate.py` exits nonzero.
3. `run_logged` raises `RuntimeError`, and `stopping_on_failure` sets `self.failure` and `stop`. The loop ends with "The
   loop stopped on a failure".

The loop's own searches meet the same failure and go down the designed path: retry, then `recover_servers`, which
restarts the dead server. They usually lose the race, because the evaluation fails as soon as its first request fails.

`recover_servers` also restarts a server deliberately while the evaluation is still sending it requests
(`stop_model.sh`, then `serve_model.sh`). That kills the evaluation, and the loop stops. The new docstring's claim that
"An evaluation beside sampling goes on" is therefore wrong in effect.

There is a second-order problem. When the evaluation's failure sets `stop` in the middle of `recover_servers`, the run's
`finally` cancels the session during `start_server`. The `bash serve_model.sh` subprocess is not killed on cancellation,
which can leave a half-started server behind. That path already existed, but before this commit nothing triggered it.

Before this commit, evaluations ran only inside the pause. The documented `restart_dead_servers` recovery therefore
covered all of sampling. Now it covers only the time when no evaluation is running.

**Reproduction:** `test_repro_beside.py` (scratchpad) uses a fake evaluation that fails once a server is down, as the
real job does. The loop stops with `RuntimeError: grpo_evaluate.py failed: ConnectError`. `servers.restarted == []`:
the server was never restarted.

**Fix:** In `evaluate_beside_sampling`, catch `Exception` from `run_evaluation`, as `score_value_benchmark` already does:

- log an `Alert:` line and count the failure in the status;
- do **not** call `mark_evaluated`, so the kind stays due. `due_beside_sampling(at_start=False)` then runs it again after
  the next pause (it needs a new version anyway), and a restart runs it through the existing `phase > 1` path;
- stop the loop only after N consecutive failures of the same kind.

Optionally, have `recover_servers` wait for or cancel the running evaluation before restarting, so that the restart
never kills an evaluation job silently.

**Confidence:** high on the mechanism (code read and reproduced with a fake). How often it fires depends on how often
servers fail.

### 2. The pause waits without limit, so a long evaluation stretches the phase's data and its training can hit the trainer timeout (medium)

**Where:**

- `loop.py:891-896` (`watch`) and `loop.py:1391-1399` (`finish_evaluations_beside_sampling`).
- `loop.py:774-779` (`work`): the limit only stops *new* statements.
- The training timeouts: `loop_config.py:93-98` and `loop_services.py:419-427`.

**Scenario:**

1. A phase becomes due, so `watch` blocks on the evaluation task. The first 56 workers keep sampling into the same
   phase, because `collecting` does not change until `run_phase`. `max_sampling_minutes` is no longer an upper bound.
2. At a fresh start the evaluation task runs, one after another (durations are estimates):
   - version 0's probe baseline: 3 parts × 2 runs, each up to a 30-min per-problem cap;
   - the miniF2F baseline: 64 expansions with a 2-hour per-problem cap (`loop.toml` has at_start = true).

   That is several hours in which phase 1 collects at 56 concurrency. A miniF2F request later in the run does the same
   to whichever phase follows it.
3. The policy (and value) training in `phase.toml` is one pass over all of the phase's trees, so training time grows with
   them. Phase 1 gets `first_train_timeout_minutes = 45`, and that budget includes model building and compilation. A
   later stretched phase gets 2 × the median of earlier phases of the same kind.
4. A timeout gives `TrainerDiedError`, a second attempt, then "Phase … failed twice", and the loop stops.

Nothing alerts while the pause waits, apart from one log line.

**Fix:** Bound the phase rather than the evaluation. Possible ways:

- cap the trees or groups a phase trains on, e.g. take the newest N;
- scale the train timeout by the phase's tree count instead of by wall-time medians;
- once the phase is due and an evaluation still runs, put new trees in the next phase. They are still on-policy
  (version k), just trained one phase later;
- stop waiting after a configurable maximum, cancel the evaluation and leave it due.

Also log the wait periodically, with an alert past a threshold.

**Confidence:** medium. The mechanism is certain; whether the timeout actually fires depends on real evaluation and
training durations.

### 3. The probe and miniF2F results now depend on load, and differently per phase (medium-low)

**Where:**

- `loop.py:774-779`: workers at index 56 and above finish their current search first.
- `loop.py:1011-1013` and `loop.py:954`: the benchmark scoring and the evaluation start together after the resume.
- The per-problem caps: `loop.toml:176` and `loop.toml:201`.

**Scenario:** The per-problem wall caps (1800 s for the probe, 7200 s for miniF2F) exist "so that the expansions are
the budget and the result does not measure load". Beside sampling, the GPUs and the Lean cores are shared with load
that varies by phase:

- In the first minutes after a resume, all 112 searches are still running: the limit only stops new statements.
- After a phase that published a value model, the value benchmark is scored through the value servers at the same
  moment the evaluation starts.
- Version 0's baseline ran under a different mix: no paused searches resuming, and the v0 scoring only if it was
  missing.

So `wall_clock_stops`, and with it the solve rate, correlates with value-publishing phases and with the time since the
resume. The bias is probably small, given the A/B (no solve after 30 min), but it is systematic.

**Fix:** At least alert when `summary.wall_clock_stops` exceeds what the baseline saw. Optionally:

- start the evaluation only after the searches above the limit have drained (`searches_running <= limit`);
- order it after the benchmark scoring;
- raise the caps for the beside mode.

**Confidence:** medium on the mechanism, low on the magnitude.

### 4. Host memory: 168 live REPLs, a budget that is reported but not enforced, and an orphaned evaluation job after an OOM kill (medium-low)

**Where:**

- `loop_services.py:672-678` (`evaluation_repls`) and `host_memory.py:58`.
- `loop.py:1378-1389`: the beside path calls no `release_lean_memory`.
- `loop_services.py:217-247` and `experiments/grpo_evaluate.py`: there is no parent-death watchdog.

**Scenario:**

1. The workers above the limit go idle, but their REPLs stay in the pool with all the memory they have grown.
2. The evaluation adds 56 REPLs, so the shipped config has 168 live REPLs where the budget was sized for 112.
   `budget_conditions` only renders "OVER" in a log line.
3. If the OOM killer picks the loop process, the evaluation job (in its own session) keeps running.
4. The next `grpo_loop.sh loop` refuses to start (`earlier_jobs`, children/evaluation.pid) until someone kills the job
   by hand. Until then the orphan keeps loading the servers.

Before this commit, evaluation jobs ran only during pauses, so both the window for this and the memory pressure were
much smaller.

**Fix:**

- When an evaluation starts beside sampling, stop the idle REPLs above the threshold:
  `pool.stop_processes(...)` on idle REPLs, which replay on next use.
- Give `grpo_evaluate.py` the persistent trainer's `--loop-process-id` / `--loop-start-ticks` watchdog, or use
  `PR_SET_PDEATHSIG`.
- Consider refusing to start when the configured budget is over.

**Confidence:** medium.

### 5. While `watch` waits it neither saves `sampling_seconds` nor refreshes the statements (low)

**Where:** `loop.py:886-899`.

**Scenario:** During the wait, which can last hours (finding 2), the `elif` branch that saves `sampling_seconds` every
`check_seconds` and the `statements.refresh()` call both stop:

- A non-graceful death (SIGKILL or OOM) loses all sampling time since the wait began. That time is part of the
  evaluation clock (`loop_seconds`), so the schedule drifts too. A SIGTERM stop is fine: `run()` saves in `finally`.
- Newly verified statements do not join the curriculum during the wait.

**Fix:** Wait in a loop instead, e.g. `asyncio.wait({task}, timeout=check_seconds)`, saving progress and refreshing
on every tick.

**Confidence:** high on the mechanism; the impact is low.

### 6. Turning `beside_sampling` off across a restart moves a cut-off evaluation to the next pause and to the next version (low)

**Where:** `loop.py:1352-1364`.

**Scenario:**

1. A stop cuts off phase k's probe beside sampling.
2. The operator sets `beside_sampling = false` and restarts.
3. `due_beside_sampling` returns `[]` because every kind is now `at_the_pause`, and `paused_evaluations(at_start=True)`
   holds only kinds due at the start. The probe is not run at the start.
4. It runs at phase k+1's pause instead and measures version k+1. Slot k's version is never measured.

A related case is switching an existing loop from `value_model = "initial"` to `"published"` mid-run. The rolling
"last `probe_parts` slots" line then mixes slots measured with value v0 and slots measured with the published value
model.

**Fix:**

- At the start, run what `due_beside_sampling` would have run as paused evaluations when the mode is off.
- Log, or refuse, a change of `evaluation.value_model` on a loop that already has probe slots.

**Confidence:** high; this is an operator edge case.

### 7. Latent: an evaluation task cancelled by anything other than `run()` would hang the loop (low; not reachable today)

**Where:** `loop.py:1398`, `await task`.

**Scenario:** If any future code cancels `self.evaluations_beside_sampling` while `watch` awaits it, `watch` receives
`CancelledError`. `stopping_on_failure` catches only `Exception`, so the cancellation passes through the session's
`gather`. The session task ends as cancelled without setting `stop`, and `run()` waits on `stop.wait()` forever.

Today only `run()`'s `finally` cancels the task, after `stop` is already set. Cancelling `watch`'s wrapper also cancels
the evaluation task, together with `run()`'s own cancel. Both happen in one synchronous stretch, so `run_logged`'s
cleanup is not interrupted.

**Fix:** In `finish_evaluations_beside_sampling`, use `await asyncio.wait({task})`, which neither propagates nor
forwards cancellation, followed by `task.cancelled()` → `stop.set()`.

**Confidence:** high that the latent path exists; it is not reachable now.

### 8. phases.jsonl and the PhaseTiming line no longer show the probe and miniF2F (low)

**Where:** `loop.py:997-1006` and `loop.py:1512-1541`.

**Scenario:** `close_phase` records `evaluations=tuple(kinds)` and `evaluation_seconds` for the paused kinds only. Probe
and miniF2F runs beside sampling appear in no phase record. Whatever reads phases.jsonl or the pause timing for
"which evaluations ran after phase k, and how long" now under-reports.

**Fix:** Append a record, or a family line, when `evaluate_beside_sampling` finishes, with the kinds, the phase and the
duration.

**Confidence:** high; the impact is cosmetic or analytic.

### 9. Tests: one passes for the wrong reason, and the risky paths are untested (low)

**Where:** `tests/rl/test_loop.py:626`, `test_evaluations_beside_sampling_swap_no_value_model`.

**The wrong-reason test:** With `value_model = "published"`, `serve_value_model` is a no-op whether or not
`beside_sampling` is on. The test therefore passes with `beside_sampling = false` and duplicates the existing
`test_evaluations_need_no_value_swap_while_the_reference_is_published`. It does not check that nothing swaps
*while sampling*. A useful version would have the fake servers assert, on every `serve`, `serve_value` or `release`,
that no evaluation is in flight.

The other new tests are genuine. I checked that each would fail under the obvious regressions:

- `most_in_flight == 1` needs the limit, because two fake workers overlap at their `sleep(0.001)`;
- probe runs at the pause == 3;
- slot 0 twice after a restart.

**Missing:**

- a server failure, or `recover_servers`, during an evaluation beside sampling (finding 1);
- an evaluation that fails beside sampling;
- a restart from a stage other than `SAMPLING` with the probe due: `finish_phase` in `session`, then
  `due_beside_sampling(at_start=True)` with `phase > 1`;
- the early resume with handed-off merges, asserting that the evaluation starts only after `record_durably`, so that
  `current.json`, the evaluation directory and the summary the loop reads agree.

## Checked and found correct

- **No sleep or weight swap under an evaluation.**
  - Weights change during sampling only in `publish`, `roll_back`, `release` and `serve_value_model`. The first three
    run inside `run_phase`, after `watch` awaited the task.
  - `serve_value_model(PUBLISHED)` matches `served_value_weights` on every path: session start, `publish` without a
    handoff, `record_durably` with one (awaited before the stage reaches EVALUATING), and `roll_back`. So it never
    swaps.
  - The one exception is `recover_servers` (finding 1).
- **Version consistency.** `SubprocessEvaluations` and `grpo_evaluate.py` both read `current.json`, which cannot change
  while the evaluation runs: the durable record is awaited and the rollback happens before the task starts. The
  `phase` argument is the closed phase, both after a pause and at a restart (`progress.phase - 1`).
- **Progress writes.** `save_progress` and `mark_evaluated` run synchronously on the event loop thread, always on the
  latest `self.progress`. No code holds a stale copy across an await while the evaluation runs, and `finish_phase`
  never overlaps the task. The evaluation subprocess only appends metrics lines and evaluations.jsonl.
- **Restart.** A cut-off evaluation is due again by schedule, since `loop_seconds` does not move during sampling, and
  `due_beside_sampling(at_start=True)` adds it when `phase > 1`. Duplicates are removed by iterating `EvaluationKind`.
  A finished one is marked with no await between the job's end and `mark_evaluated`, so it does not run twice.
  Phase 1 restarts reuse the at-start baseline logic with `probe_slots` kept per slot.
- **Cancellation.** The task is cancelled twice, by `watch`'s wrapper and by `run()`, but both requests arrive before
  its next step, so `run_logged`'s `finally` / `stop_job` runs uninterrupted and the job is stopped.
- **`asyncio.wait`.** `asyncio.wait` on the wrapped task in `work` is safe: the wrapper never raises an `Exception`,
  and `wait` does not cancel it.
- **`pause_lock`.** No deadlock: the task never takes `pause_lock`, and `watch` waits outside it.

## Blockers

- **Finding 1** should be fixed before a long run. With the shipped config, a single server crash or overload-induced
  failure during a probe slot or the at-start baselines ends the loop instead of being recovered. That is a
  regression of `restart_dead_servers`. The fix is small: make an evaluation failure beside sampling non-fatal and
  leave the kind due.
- **Finding 2** is a likely blocker for the first phase of a fresh loop. The pause waits hours for the baselines while
  phase 1 keeps collecting, and that phase's one-epoch training then risks the 45-min first-train timeout.
  - Bound the phase's training data, or scale the timeout.
  - At minimum, measure phase 1's tree count and training time in the smoke cycle at the real baseline sizes.
- Findings 3-9 are not blockers. Finding 4's watchdog and idle-REPL release are cheap and worth doing alongside.
