## Findings, by severity

### 1. (Medium, deployment) Deploy the merge into master, not the branch tip: 94edc23 lacks master's 860d1c2

**Where.** `src/lean_search/rl/loop.py:811-823` (`GrpoLoop.work`) on the branch.

**Scenario.**
- The branch forks at a9ba257. Master's 860d1c2 ("idle search REPLs stop once per evaluation run, not whenever the
  sampling limit moves (one probe slot restarted them 3,192 times)") is not in it.
- `git diff 860d1c2 94edc23 -- src/lean_search/rl/loop.py` shows the branch putting back the per-wait
  `stop_idle_repls` in `work()`.
- If the node runs `origin/search-variants` itself (a checkout of the branch rather than of the merged master), the
  probe slots beside sampling restart the same REPL processes thousands of times again.
- The three-way merge is clean and keeps master's version (checked in the merged tree, `loop.py:814`).

**Fix.** Merge into master and deploy master. Or rebase the branch on 860d1c2 first, so that the branch tip and the
deployed code are the same.

**Confidence.** High.

### 2. (Low-Medium) The loop's tree-based health signals mix the feedback round's samples into baselines that had none

**Where.**
- `rl/tree_summary.py:68-101`: `policy_samples`, `distinct_blocks`, `distinct_texts`, `cut_off_samples`,
  `judged_blocks` and `valid_blocks` count every POLICY edge and completion, feedback ones included.
- `rl/health_checks.py:66-87` (`measurements`) feeds them to thresholds taken from the first `reference_phases` (2)
  phases, which had no feedback.
- `rl/loop.py:1197`: a `VALID_BLOCKS` alert requests a held-out evaluation for the next pause.

**Scenario.** With the A/B on, half the statements add a 4-sample round at every expansion whose 8 samples reached
fewer than 2 new states and failed.
- **Valid blocks.** These are the nodes where the policy writes invalid Lean, so the round's blocks are likely to be
  less valid than the first round's. `valid_block_rate` drifts down.
  - Below 85% of the reference it warns and adds a 112-REPL held-out run to the next pause.
  - The drift is probably a few percent at the expected trigger rates, but it eats the margin of a check meant to
    catch the policy degrading.
- **Distinct samples.** `distinct_samples_per_expansion` rises, because a triggered expansion gets up to 4 more
  distinct blocks. That masks part of a real collapse in the "Samples collapsing" check.
- **Dashboard.** The `search` family's failure tiers and unknown-name rate (`phase_metrics.py`) mix the round in the
  same way.
- **Evaluations.** The held-out, probe and miniF2F evaluations are pinned (question 3), so the rollback signal itself
  is unaffected.

Review M issue 5 asked for first-round-only counting here; the commit pinned the evaluations but not these.

**Fix.**
- In `tree_summary`, count only `not edge.feedback` edges and the completions of `ExpansionTexts` with
  `feedback = False` for the health fields.
- Optionally add the feedback round's own counts as separate fields.
- Alternatively, compute `measurements` from control-arm entries only while the A/B runs.

**Confidence.** High on the mechanism, medium on the size. Stage 0's trigger rate and the A/B's first phase will
show it.

### 3. (Low-Medium, deployment) A probe slot or miniF2F run cut off by the deploy restart fails on resume: its config.toml was written by master

**Where.**
- `rl/evaluation.py:470-475` (`keep_config` compares the TOML text).
- `rl/loop.py:1442-1447` (`due_now`: at a start, the evaluations "a stop cut off" are due again). They run for the
  same version, into the same directory (`GrpoLoopPaths.evaluation_directory`, `loop.py:412-416`).

**Scenario.**
- `run_config_text` now always writes `[search.name_repair]`, `policy.failed_automation_in_prompt` and
  `[policy.feedback]`, all at their defaults (`eval_config_text.py`: 15 added lines, nothing else differs).
- The loop is stopped for the deploy while a probe slot or a requested miniF2F run is running beside sampling. On
  restart that run is due again for the current version k. Its directory holds master's `config.toml`, so it raises
  `ValueError: ... holds another config`.
- `evaluate_beside_sampling` catches it:
  - it logs an alert and counts an evaluation failure;
  - the run is retried only after the next pause, under version k+1;
  - version k's slot is lost.
- The held-out states have no config check, so the pause's own evaluation is unaffected. Resuming a
  `grpo_evaluate.py` run by hand fails the same way.

**Fix.**
- **In code.** Compare parsed configs, `parse_run_config(paths.config.read_text()) == config`. New default-valued
  fields then compare equal.
- **Operationally.** Restart when no evaluation runs beside sampling. Or delete the current version's `evaluations/*`
  directories that have no `summary.json` before the restart.

**Confidence.** High on the mechanism (reproduced text diff). Whether it happens depends on the restart's timing.

### 4. (Low) The A/B's per-arm record measures tokens but not the round's wall-clock and Lean cost; its token count includes post-solve harvesting

**Where.** `monitoring/families.py:91-100` (`ArmOutcome`), `rl/budget_signals.py:69-97`, `rl/tree_summary.py:101`.

**Scenario.**
- **Missing costs.** The feedback round's main costs besides tokens are:
  - a second, sequential policy request per triggered expansion;
  - 4 more blocks in Lean.

  The arms share the 112 REPLs, so the slower arm also takes REPL time away from the control arm. `ArmOutcome` has
  only trees, solves, trainable groups and generated tokens. The `trees` count per phase shows throughput only
  indirectly.
- **Tokens after the solve.** `generated_tokens` is the whole tree's. That includes the harvest's 16 expansions after
  the first proof, where the round also fires. So "solves per million tokens" charges the feedback arm for tokens
  that bought no solve.
- **Group counts.** `trainable_groups` counts a node's feedback group as one more group. So "trainable groups per
  tree" is not "nodes with signal", and a 4-sample group weighs like an 8-sample one.
- **No interval.** There is no confidence interval. The loop.log line is point estimates per phase.

**Fix.**
- Add to `TreeSummary` and `ArmOutcome`:
  - wall seconds per tree (already in `TreeEntry.wall_seconds`);
  - Lean seconds and expansions per tree;
  - `solved_at.generated_tokens` for solved trees;
  - trained sequences, or proof-graph nodes with a signal.
- Bootstrap over trees offline from the index, since `TreeSummary.arm` makes that possible.
- Keep in mind that both arms train one policy. The A/B measures the search-time effect only. Any effect of training
  on feedback groups lands in both arms; the pinned held-out evaluation is what guards the base prompt.

**Confidence.** High.

### 6. (Info) REPAIR edges: harmless, two small counting quirks

**Where.** `search/search.py:635-643` (`_run_repair`) and `rl/tree_statistics.py:235,241`.

**What I checked.** Repair edges are:
- never in a group (`grpo_groups.py:235`);
- never in `policy_tactics` (`tactic_labels.py:204`), and so never a policy proof;
- not in `tree_summary`, `phase_metrics` or `search_option_analysis` (each filters on POLICY);
- outside `step_statistics`' policy key (they get their own `<repair>` key);
- scored by `CumulativeLogProbability` (`priority.py:65`).

States a repair reaches are real Lean states, so their use in graph labels and value targets is sound. No
`edge_id_by_text` entry points at a repair, so no policy sample can be a REPEAT of one. A later sample that wrote the
repaired text runs as its own edge, and reaches the repair's state as a DUPLICATE that is credited to the policy.

**Quirks.** `_run_repair` copies the sample's candidate, so a repair edge carries the sample's `forced` flag,
`sample_count` and token fields.
- `graph_statistics.forced_edges` counts a repaired forced sample twice.
- `edges` and `partial_failures` include repairs.

None of this applies to the planned A/B (name repair stays off).

**Fix.** Set `forced=False` (and zero tokens) on the repair candidate, or filter POLICY in `forced_edges`.

**Confidence.** High.

## Answers to the questions

### 1. Loop safety with the A/B on

**Arm assignment and recording.** These are correct and consistent (finding 5). `TreeSummary.arm` defaults to "", so
old index entries read. `by_search_arm` includes only entries with an arm and is empty with the A/B off. The loop.log
line is written once per phase in `check_health`.

**Feedback groups.** Feedback groups train on their exact prompts:
- `policy_groups` splits each node's samples by `Edge.feedback`.
- `tree_policy_data` looks texts up by `(node_id, feedback)`.
- Advantages are per group, and the persistent trainer goes through the same `prepare_policy_tree`.

The simulation checks the prompt bytes and the edge-to-group mapping. A feedback sample repeating a first-round block
is a REPEATED edge in the feedback group, with the first-round edge's tactics. Its completion is in the feedback
texts.

**Pause gate.** `GatedExpander` enters the gate for every `anext` and reads `policy_version` after entering. The
feedback request is that second `anext`, made only after the search ran the first batch. A pause between the rounds
holds it, and the resumed request carries the new version. This is in the simulation, with the overlapped composite
the loop uses. Each round's `ExpansionTexts` keeps its own version.

**No feedback after a proof.** `feedback_fires` checks every CHILD edge at the node, the sweep's and repairs'
included, for a verified proof. Proved states are never deduplicated (`search.py:716`), so a proof is always a CHILD.
In the simulation, with harvesting on, neither a sweep proof nor a policy proof triggers a round. A failed
verification (node FAILED) does not count as a proof, which is right.

**Tokens and credit.** The round's tokens are charged like any batch, before it runs. `solved_at` includes them only
when the round precedes or makes the proof. `TreeSummary.generated_tokens` is the tree total; see finding 4 for how
the A/B uses it.

**Curriculum and statement sources.** No code change touches them. Both arms feed the same cohorts. Slower
feedback-arm searches are somewhat more likely to be among the cohort's last 10% that is judged unsolved. That
affects the band equally for both arms and is not in the per-arm numbers, which count finished trees.

**Feedback round wiring.** `PolicyExpander.expand` sends `sample_count=4` with `feedback=True`. The batch's
`temperature` is recorded per batch, so an arm with its own temperature would also train at the right temperature.
HTTP errors in the round take the existing retry path.

### 2. Repair edges

Never trained and never a policy proof (`has_policy_proof` reads only POLICY tactics). Harmless to graph labels,
value targets, budget signals and the dashboard, apart from the counting quirk in finding 6. They are off in the
planned A/B.

### 3. The pinned evaluation template

Every loop evaluation goes through `evaluate_target`, which applies `without_search_options` first:
- the held-out states at the pause, through `evaluate_held_out_states`;
- the probe and miniF2F, through `evaluation_run_config`;
- the version 0 baselines;
- the value arm;
- `grpo_evaluate.py` run by hand;
- `grpo_naming_ab.py`.

`single_step_run_config` then sees `failed_automation_in_prompt = False`, so the held-out run stays policy-only.

Moreover, the evaluations' template is `sampling.search_config`, which the A/B never changes: `options_arm` is applied
only in `open_tree_searcher`. So the evaluations run with options off for two independent reasons. The paths that
bypass `evaluate_target` are not loop evaluations:
- the gate benchmark (`gate_search.toml`, run once);
- `grpo_single_step.py`;
- the harness.

### 4. Record compatibility

- **Old trees and the store.** A master-written `TreeStore` reads with the new code, and the persistent trainer's
  preparation of policy data and value windows works on it (`read_old_store.py`, `trainer_window.py`). Every new
  field has a default. `PolicyGroup.feedback` and `TreeSummary.arm`/`generated_tokens` default to off/0.
- **The persistent trainer.** It stops with the loop process and starts with the new code at the first `prepare`
  (`PersistentTrainer` docstring), so no old-code trainer reads new trees.
- **Caveats.** Finding 3 (a resumed evaluation's `config.toml`) and finding 7 (rollback).

### 5. Behaviour with every option off, against 860d1c2

These are the differences, beyond finding 1 (branch tip vs merge) and finding 3 (resuming evaluations):
- **Records.** Two default-valued keys per edge and one per `ExpansionTexts` are written (rollback only, finding 7).
- **`GatedExpander`.** It now enters the gate for the policy generator's final, exhausting `anext`. A search whose
  policy batch finished during a pause now waits at the gate instead of going on to `_enqueue` or a sweep. That is
  harmless (Review L), and the paused REPLs are stopped anyway.
- **`CompositeExpander`.** It prefetches only the first batch of the later expander. That is identical with one batch
  per expander.
- **`search_states`.** It cancels the other searches when one fails.

Unchanged:
- **Search config and prompts.** `without_search_options` is the identity, `options_run_config` round-trips, and the
  prompts are byte-identical (`user_message` adds sections only when given).
- **Rejection text.** The identifier check's rejection text is unchanged.
- **Metrics.** `sample_success` and `TreeSummary` give the same numbers (verified on a master-written tree).

## Verdict

**Safe to merge to master, and safe to run the loop with the feedback A/B on**, provided that:
- the node runs the merged master, not the branch tip (finding 1);
- the restart is timed so that no probe or miniF2F run is cut off, or its partial directory is removed (finding 3).

The mechanics the A/B exercises are correct, and I checked them end to end:
- the arm split;
- separate feedback groups on their exact prompts;
- the gate and version labels for the second request;
- no round after a proof;
- token accounting;
- pinned evaluations;
- reading the existing store and window.

  are not shifted by it;
- add the cost fields of finding 4, so the decision weighs wall-clock and Lean time and not only tokens.
