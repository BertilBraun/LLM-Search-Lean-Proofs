## Highest priority: can the normal case (no rejected versions) drop or corrupt training data?

**No. I found no path that does.**

- **`excluded_policy_versions = ()`.**
  - `phase_config_text` writes `excluded_policy_versions = []` as a top-level key. `toml_text` writes the scalars first,
    so the key cannot fall into the last table.
  - It parses back to `()`.
  - `groups_not_sampled_by` builds an empty excluded set, so every group is kept.
  - `sampled_by` is `False` for every tree, so `value_window` and `label_value_trees` keep every tree.
- **Version labels.**
  - `None` (old trees, outside the loop) is never in the excluded collection.
  - An expansion missing from `record.expansions` excludes nothing.
  - `GatedExpander` reads `gate.policy_version` after `enter()`. A batch that waited through a swap therefore carries the
    new version.
- **`read_tree(texts=False)`.**
  - Value labelling never touches `record.expansions`: `label_graph`, `recorded_estimates` and `value_targets` use only
    nodes and edges.
  - In the loop, `tree_summary` runs only on the in-memory record.
  - `normal_case_check.py` checks policy versions None, 0 and 3, each with the default config, an explicit `()` and an
    unrelated `(99,)`. All give identical policy trees and labelled trees. Value targets and labels are identical with
    and without texts.
- **Preparation reuse.**
  - `prepare_training` and `train` both build the config through `training_request`, and both read the same (empty)
    `rejected_versions.jsonl`. The persistent job's `matches()` therefore still reuses its preparation.
  - After a rejection the texts differ, so the job prepares the phase again. That is correct, only slower.
- **Value window in the persistent job.** It now prepares a tuple per tree and flattens it at `train_value`. The
  empty-list case gives the same window as before (`test_preparation_while_sampling_labels_the_value_window`).

## Findings, by severity

### 1. (Medium-Low) The per-phase A/A balance check runs on trees *finished* in the phase, so it can raise a false "routing broken" alert at the A/B's last phase, at the same check as look 6

**Where.**
- `loop.py:1275-1281`: the alert.
- `options_ab.arm_outcomes` / `arm_balance` (`options_ab.py:171-247`), fed by `budget_phase_record` over
  `store.phase_entries(phase)`.

**Scenario.**
- `max_phases` switches the arm off at `collect(first + 6)`, the start of the 6th A/B phase's pause.
- The next phase's directory then holds, in the arms, only the trees that were in flight at that pause. Those are
  length-selected:
  - control trees in flight are the slowest control statements;
  - feedback trees in flight include more ordinary statements, because the round lengthens every tree.
- So mean difficulty, verified share and the root's first-round valid rate differ between the arms by selection.
- The check then logs `Alert: ... the split or the routing may be broken, the A/B's result is not one`. Look 6 fires
  at that same phase's check (finding 4).
- The same selection, weaker, applies to the A/B's first phase after the restart that enabled it.
- There is also multiplicity: 4 metrics at 99% each give about a 4% false-alarm rate per phase even in steady state,
  about 20% over 6 phases.

**Fix.**
- Run the balance on the look's population (trees by start phase, `options_look`'s `population`) and report it beside
  each look. Alternatively, skip the per-phase alert when the arm did not run for the whole phase: the phase's arm
  entries have a `start_phase` other than the phase.
- Correct the alert for multiplicity, or require two consecutive phases before alerting.
- No training data is affected.

**Confidence.** Medium on the mechanism. The size depends on how many trees span the pause (about 112).

### 2. (Low-Medium) First-round KL and the all-sequence KL take different medians, so the KL health series shifts at deployment without any drift

**Where.** `policy_trainer.py:724-725` against `:737`.

**Scenario.**
- With `kl_coefficient = 0`, only `reference_sequences = 256` sequences per phase are scored under the reference
  (`reference_sample`).
- A 64-sequence step with no scored sequence reports `kl_to_reference = 0 / max(1, 0) = 0`:
  - `final_kl_to_reference` takes the median over *all* last-pass steps, zeros included;
  - `final_first_round_kl_to_reference` skips steps without first-round reference tokens.
- So even without any feedback sequence the two disagree. `test_without_feedback_sequences_the_first_rounds_kl_is_the_whole_kl`
  checks one step record, not the final value.
- `reference_steps.py` (heavy-tailed per-sequence KL, median about 0.05):

  | sequences per phase | steps unscored | all-sequence median | first-round median |
  |---|---|---|---|
  | 8,000 | 10% | 0.057 | 0.064 |
  | 12,000 | 22% | 0.041 | 0.053 |
  | 16,000 | 40% | 0.021 | 0.059 |
  | 24,000 | 50% | 0.000 | 0.058 |

- The old metric was biased low. The new one is closer to the truth, but the `kl_to_starting_policy` series jumps at
  the first phase trained by the new code. The 0.5 threshold is a warning only, so nothing acts on it.
- The first-round clip fraction is consistent: every step has trained tokens.

**Fix.**
- Give both metrics the same rule. Skip steps with no reference tokens in the all-sequence median too, or better, use
  a token-weighted mean over the phase.
- Note the level shift beside the first phase trained after the restart. Check `policy.data.sequences` in a recent
  `phase.json` for the size of the effect.

**Confidence.** High on the mechanism. The magnitude depends on the sequences per phase.

### 3. (Low) The early-resume guard sits exactly on the collapse line, and the partial rate is optimistic

**Where.** `loop.py:1765`, `early_resume_floor` (`:1786`).

**Scenario.**
- At `generation_finished` the states still in Lean are the slow ones. Timeouts count as not valid, so the rate over
  the finished states runs above the final rate.
- With the floor at 0.7 × version 0's, a version whose final rate lands just under the line often passes the guard.
- The consequence is now bounded:
  - the rollback pauses before its merge;
  - the version's groups and trees are dropped from training.
- What remains is a few minutes of searches on a collapsing policy, and their statements consumed and recorded as
  curriculum failures.
- Review P asked for a 0.8 × margin and for a cap on the job's REPLs in flight. Neither is implemented; the docs now
  state the 112 + ~110 REPL peak instead.

**Stale or partial progress.**
- I found no stale read. `evaluate` unlinks `progress.json` before the job starts, the file is written atomically, and
  an old file without `samples` reads as `None`, which holds back.
- After a restart the job counts only the states pending in that run. But a restarted loop starts with
  `paused = False`, so it never resumes early there.

**Fix.** A floor of `max(collapse line, 0.8 × version 0's)`, or a margin parameter in `[health]`.

**Confidence.** High.

### 4. (Low) Look timing: one phase later than the docs say; a missed look is skipped silently; a partial first A/B phase counts in full

**Where.** `options_ab.options_look` (`:357-367`), `options_ab_phases`, `options_arm_finished`.

**Scenario.**
- **Timing.**
  - Look k fires at the check of phase `A/B phase k + 1`: `phase - 1` must be the k-th start phase. That is deliberate
    (the docstring says so), so the trees started in phase k can finish.
  - DESIGN.md, `rl/README.md` and `loop.toml` say "looks after A/B phases 2, 4 and 6". With A/B phases 6-11 the looks
    fire at the checks of phases 8, 10 and 12, and look 6 comes one phase after the arm switched off.
- **Old index lines.**
  - Entries written by 60ab89f have `started_phase = 0`, so `start_phase` falls back to the phase they finished in.
  - A tree that started in A/B phase k under the old code and finished in k+1 counts in k+1. That moves a few long
    trees between pools at the boundary. It cannot move a look to another phase, because the phase still has its own
    starts.
- **Missed look.** If the restart comes after the check at which a look was due, that look never fires. Nothing
  catches it up.
- **Partial first phase.** If the restart that enabled the A/B came in the middle of a phase, that phase counts as a
  full A/B phase toward `max_phases` and look 2.
- **No look at the wrong phase.** I found no sequence that makes a look fire at the wrong phase, given that the A/B ran
  phase 6 on the older code.

**Fix.**
- Change the docs to "at the check after A/B phase k + 1 (the trees started in phase k have finished)".
- Before the restart, print the schedule on the node:
  ```
  PYTHONPATH=src python -c "
  from pathlib import Path
  from lean_search.rl.tree_store import TreeStore
  from lean_search.rl.options_ab import options_ab_phases
  phases = options_ab_phases(TreeStore(Path('<run>/trees')).entries, 'feedback')
  print('A/B start phases so far:', phases, '; arm ends at collect', (phases[0] + 6) if phases else None)
  print({k: (phases[0] + k) for k in (2, 4, 6)} if phases else None, '(look k at the check of this phase, if contiguous)')"
  ```
  If the first A/B phase was partial, consider `max_phases = 7`.

**Confidence.** High.

### 7. (Low, design) A manual rollback rejects only the current version

## Other questions, answered

- **Restart compatibility.** Intact. Every field this diff added has a default, and `from_json_object` accepts missing
  keys that have defaults:
  - `TreeEntry.started_phase`, `paused_seconds`, `verified`;
  - `TreeSummary.root_*`, `sampling_versions`;
  - `LoopProgress.next_phase_sampling_seconds`;
  - `GrpoTrainingResult.final_first_round_*`;
  - `SearchProgress.samples` and `valid_samples`;
  - `GrpoStepRecord.first_round_*`.

  `measurements` falls back to the all-sequence KL and clip for an old `phase.json`. The persistent trainer does not
  survive a loop restart: its ranks stop with the loop's process, and the restart refuses to run while they live. So no
  old trainer ever sees the new config key. Evaluation `config.toml` (RunConfig) is unchanged. A missing
  `rejected_versions.jsonl` reads as `()`. If the live run ever rolled back (`versions.jsonl` trigger
  `rollback to ...`), that version is not retroactively rejected; append its line by hand if wanted.
- **Arm at search start.**
  - Correct across server-failure retries: each retry is a new `SearchStart`, with the same hash arm, or `""` once the
    A/B ended.
  - Correct across restarts: killed searches are re-fed with the same hash.
  - Correct across the switch-off: `collect` runs at the pause start, so statements taken during the pause start with
    the template, and searches in flight keep their arm and their start phase.
  - On restart, `__init__`'s `collect(progress.phase)` and the "Finishing phase" `collect(phase + 1)` recompute the
    flag from the index, and the log runs only on a True to False change.
  - `LeanTreeSearcher.search` asserts that the arm name matches the configured one.
  - Paused seconds use `PauseGate.paused_seconds()`, which includes the ongoing pause. A search started during a pause
    is therefore not charged for the part before its start.
- **Bootstrap.**
  - The arm and control strata are resampled within each start phase, independently (one generator, drawn in turn).
  - The point estimate is the ratio of pooled sums.
  - NaN draws are dropped. NaN bounds make every comparison false, so the verdict is `CONTINUE`.
  - The thresholds and confidences match the rule in DESIGN.md.
  - The dashboard server writes non-finite values as null.
- **Pause before the merge.** `roll_back` now pauses before `publish_rollback`
  (`test_a_rollback_beside_sampling_pauses_the_searches_before_its_merge` checks the order). A hard stop rejects the
  version through `collapsed(record)`: its STOP alert is the held-out collapse.
- **Sampling seconds across a stop beside the tail.** Correct. A second stop during the restarted pause does not
  overwrite them, because `sampling_since` stays `None` until the restarted session starts sampling.
