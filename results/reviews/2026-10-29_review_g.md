# Review G: owner decisions of 2026-10-29 (b088690..044f93a)

Scope: the persistent trainer (parked weights, labelling during sampling, in-memory handoff, background durable
write), the trainable-group phase trigger and the 32-expansion budget signals, per-phase health checks with the hard
stop and rollback, and the switch from value gates to trends (benchmark trend, paired value arms, manual μ, probe
thirds). Design review, no code edited.

## Verdict: go for the smoke cycle, with three cheap fixes first and four measurement changes before the main run

The mechanics are careful. Versions are never recorded before their files exist. Each restart window (after the
handoff but before the record, during the durable write, after the record but before the stage change) ends in a
consistent state. The trigger counts groups with the trainer's own functions. Tree files are written atomically, so the
labelling thread never reads half a tree. Between commands no collective is pending, so idle NCCL is harmless. Nothing
here blocks the smoke cycle.

The weak points are the statistics and the cost:

1. A trend-only feature can stop the loop. An error in the value-benchmark scoring that is not an HTTP error kills the
   loop at the next pause, and that version's trend is never written.
2. The hard stop is slow and leaves the node idle. Held-out states run every 6 h of loop time, so 4–8 versions are
   published before a collapse is seen. The stop then idles the rented node until someone looks.
3. The probe in thirds is plotted raw. The thirds differ in difficulty by about as much as the run-to-run noise
   (simulated), so the per-slot curve has a period-3 sawtooth of the same size as the effects it is meant to show.
4. The value arm is weak and covers value versions unevenly. Some versions get no arm, others two. It catches a
   5-point harm about a quarter of the time. Over the run it should raise 1–2 false "worse" alerts, at about 6% of
   wall time.

Evaluations as configured take about 15–21% of wall time (estimate below), more than the 10–15% DESIGN states.

## Findings

### Major

**M1. A non-HTTP error in the benchmark scoring stops the loop, and that version's trend is never written.**
`loop.py:946-960` catches only `httpx.HTTPError`. The task is awaited by `finish_benchmark_scoring` in `run_phase`
(`loop.py:841`) and in `run_evaluations` (`loop.py:1262`), so any other exception reaches `stopping_on_failure` and
stops the loop. Examples: a malformed vLLM response (`KeyError`), a `ValueError` in `bin_distribution`, or a bug in
`benchmark_trend` / `pair_statistic`. `benchmark_trend` also calls `keep_scores` (`loop.py:967`) before computing the
trend, so a failure there leaves `scores_v<k>.json.gz` behind. `schedule_benchmark_scoring` (`loop.py:937`) then never
scores that version again.

Scenario: the first retrained value model (v4) is published at the end of phase 4. Its trend raises in
`prediction_distribution`. Up to 90 min later phase 5's pause re-raises the error and the loop stops overnight. After
the restart, v4 is never scored, so the Value page has a permanent gap.

Fix: catch `Exception` in `score_value_benchmark`, log it with its traceback, and return. Write the scores only after
the trend has been computed. A trend must never be able to stop training.

**M2. The hard stop sees a collapse late, rolls back to a version that may already be degrading, and idles the
node.** The only stop signal is the held-out valid-Lean rate. It runs every 6 h of loop time (`loop.toml:202`;
`loop.py:1000-1001` reads it only when `HELD_OUT_STATES` ran this pause). With 45–90-minute phases that is one check
per 4–8 published versions, all trained on and searched with in between.

`last_good` becomes the newest version whose held-out rate stayed above the stop line (`health_checks.py:255-256`).
That includes the warning band of 0.7–0.9× v0's. Retention keeps only that one adapter beyond the last 5
(`loop.py:1151-1152`). The `--version` alternatives are pruned within about 5 phases.

On a stop the loop exits and refuses to restart (`loop.py:678-680`). A stop at 01:00 leaves 4 GPUs billed and idle
until morning. That is 6–8 h, about 3–5% of a $200 / 1-week budget per incident.

Scenario: the learning rate is too high. Valid Lean falls over phases 9–14. The held-out run after phase 8 read
0.85× v0's (a warning) and the one after phase 14 reads 0.6×. The rollback target is v8, which was already sliding,
and v9–v13's adapters are gone.

Fixes, cheapest first:
- Run held-out states with every probe slot (`every_hours = 2.0`). It is 512 single-expansion requests, about 3 min,
  so about +1.5% of wall time, and it cuts detection to about 2 h.
- Add a free per-phase pre-trigger from the training trees, for example the share of policy edges that fail at their
  first tactic, from `TreeSummary`. When it drops sharply against the reference phases, force a held-out run at that
  same pause (as `request-evaluation` does).
- Define "last good" as the last held-out version without a warning, and keep the adapters of the last 2–3
  held-out-evaluated versions.
- Offer `[health] on_stop = "rollback"`: publish last-good, halve the learning rate, and continue, so the node keeps
  sampling until the owner reviews. Whether to stop is the owner's call; the idle cost should be stated.

**M3. The rotating-thirds probe curve is confounded by which third ran.** Each slot plots the raw solve rate of its
third (`static/pages.js:54`). The thirds are fixed for the whole run and differ in difficulty by sampling chance. The
simulated offset SD is 2.3 points, against a run noise of 2.0 points and the ~3-point effects review F expects the
probe to resolve. Consecutive slots therefore show a fixed sawtooth with period 3 that looks like movement.

The "last three slots" curve removes the offset, but each point mixes three policy versions spanning 4–6 h. Neighbouring
points also share two thirds of their data, so their differences are mostly not new information.

Every part already has two v0 runs (`baseline_runs = 2`), so the fix is free. Plot each slot as its solved count minus
the mean of v0's two runs on the same part, per problem and paired, with its McNemar interval. That has the same noise
(2.4 vs 2.0 points) and no offset. Average the last three paired differences for the smooth curve, and mark only every
third rolling point as independent.

**M4. The value arm is weak, uneven across value versions, and cheap only next to the A/B it replaced.**
- Uneven: value versions last 4 phases, about 3–6 h of loop time. Arms run every other 2-hour slot (`loop.toml:177`).
  So a value version gets 0, 1 or 2 arms, about 1 on average. "Pooled over its own value arms" (`evaluation.py`,
  `value_arm_result`) is usually a single slot of ~167 problems. Some value versions are never checked.
- Weak: one arm gives the alert rates in the simulation table above (24% at a 5-point drop).
- False alerts: over the ~30–50 value versions of a 1–2-week run, expect 1–2 false "worse" alerts (`loop.py:1242`).
  The alert ships without its power.
- Cost: an arm is a full slot of searching, 13–20 min every ~4 h, about 6% of wall time.

Scenario: v12 really costs 4 points of solve rate under search. It gets one arm, which by chance falls between
retrains, and that arm shows nothing. v16 replaces it without any signal.

Fixes:
- Tie the arm to value versions: run it at the first slot after a new value model is published, exactly once per
  version, at the same average cost.
- Log the arm's minimum detectable effect next to its p-value.
- Raise the alert threshold to α = 0.01, or require two arms pooled.

If μ is ever turned on, check the benchmark trend of the current value model before the next retrain. With μ > 0 an
unchecked value model shapes the policy reward directly.

**M5. Phase-counted value settings did not follow the 3× longer phases, and the value window is still labelled
inside the pause.** `value_every_phases = 4` and `value_window_phases = 8` (`loop.toml:109-110`) were chosen for
15–30-minute phases. At 45–90 minutes the value model now retrains every 3–6 h on 6–12 h of trees (about 1,500–3,500
trees at review F's 200–280 trees/h), mostly from policies 4–8 versions old.

The window is read and labelled single-threaded on the main rank at the pause (`resident_trainer.py:264-270,
366`), with the searches paused and the other three ranks waiting in `broadcast_from_main` (`training_phase.py:302`).
This is the stage review F measured at 10–15 min for 2,000 trees before the parsing fix. The README's "1–2 minutes"
is not a measurement. After a finished phase closes, its trees never change, so this work can be done earlier.

Fixes:
- Express the cadence in hours, or rescale to `value_every_phases = 2` and `value_window_phases = 3–4`.
- Have the main rank label each closed phase's value trees during the following sampling and cache the
  `LabelledTree`s to disk per phase. The pause then only loads them.
- Measure the `preparation` segment of phase 4 in the smoke cycle.

**M6. Evaluations cost about 15–21% of wall time, and the thirds make the tail inefficiency worse.** Per 2 h of
loop time (the clock excludes evaluation and publishing, `loop.py:890`):

| Item | Wall time |
|---|---|
| Probe slot | 13–20 min |
| Half a value arm | 6.5–10 min |
| A third of a held-out run | about 1 min |
| **Total evaluation** | **~21–31 min of ~141–151 min, 15–21%** |
| Pauses (on top) | ~8–12% |

So sampling gets about 70% of wall time, against DESIGN's "~10–15% of compute".

A 167-problem slot at concurrency 64 is only about 2.6 waves. Its tail, where fewer than 64 searches run, is a larger
share of the slot than it was for the whole 501-problem set.

Fixes:
- The paused searches' REPLs are stopped before evaluating (`paused_repl_memory_gib = 0`), and the target node has
  ~240 GiB. Raise evaluation concurrency to ~112, or run the slot and its value arm in one pass with the value servers
  of GPUs 0–1 serving v0 and those of 2–3 serving the published model.
- Report evaluation seconds as a share of wall time on the System page so this number is visible.

### Minor

**m1. A hung persistent job blocks the loop for up to an hour with all GPUs idle.** `PersistentTrainer.wait_for`
(`loop_services.py:383`) has no timeout. A hang inside a collective surfaces only after `COLLECTIVE_TIMEOUT = 1 h`
(`data_parallel.py:14`), with every search paused. Fix: a loop-side timeout per `train` of a few times the median of
the earlier phases' training seconds. On expiry, `stop_job` and the existing retry-once path.

**m2. Changing μ mid-phase relabels the whole phase inside the pause, on one thread at nice 19.**
`start_preparation` (`resident_trainer.py:248-255`) discards the preparation when the config text differs, and μ is
part of that text. Fix: in `watch`, re-send `prepare` when `value_share.json` changes (compare its `set_at`), so the
relabelling happens during sampling.

**m3. Stopping every paused REPL before training is probably no longer needed.** `paused_repl_memory_gib = 0`
(`loop.toml:121,156`) was review F M6's fix for four ranks each parsing the phase. Now only the main rank holds
sequences, and the node has ~240 GiB, not the README's 128 GB (`rl/README.md:479,508`). The default still costs 112
REPL restarts and state replays at every resume, a CPU burst just as the durable write runs. Fix: measure once in the
smoke cycle, then set it to about 1.0 GiB, and update the RAM figure and the budget example.

**m4. The memory peak the README warns about is never logged.** That peak is "searches running + handoff", the
sampling condition at about 109 GiB (`rl/README.md:506-508`). The loop logs at the pause, before training, after
training and "after publishing", but the last of these runs only after `await durable` (`loop.py:903-905`), when the
handoff is already cleared. Fix: log host memory right after the early resume, and once more inside `record_durably`
before `rmtree`.

**m5. A restart in the training stage repeats work it does not need to.** After a crash between the job's reply and
`save_progress(PUBLISHING)`, the restart trains the phase again with a fresh job. That job builds its models inside
the pause (four ranks in turn on the CPU, then compile), with the GPUs idle for several minutes. Fix: when `phase.json`
and the adapter exist and the handoff markers match, go straight to publishing.

**m6. The hard stop can be silently disarmed, and its signal moves with block length.** With no v0 held-out summary,
all held-out thresholds stay unset (`loop.py:1002-1003`, `health_checks.py:119`) and no stop ever fires, without any
message. Separately, "valid Lean" means the whole block runs. A healthy shift to longer blocks lowers it as `p^L`:
from 2 to 3 tactics at 0.8 per tactic is 0.8× v0's, a warning. Fixes: log once at start when the stop is disarmed.
Report a per-tactic valid rate (the first tactic, or valid tactics over executed tactics) next to the block rate, and
consider basing the stop on it.

**m7. Some thresholds will never fire, and the late-solve note is a weak truncation test.**
- `max_kl_to_starting_policy = 0.02` (`loop.toml:216`) is 20–200× the expected 1e-4–1e-3, so it fires only on
  disaster. Set it relative, for example 10× phase 3's value.
- The share of solves in expansions 25–32 under-reacts. Under a smooth hazard, many proofs can be cut off while only a
  few percent land in the last quarter. Report the hazard there (solves in 25–32 / searches alive at 24) times the
  survivors at 32 as the estimated extra solves per doubling of the budget.

**m8. One unusual tree can stop the loop during sampling.** `tree_summary` runs in `work` outside the `try`
(`loop.py:738-740`), so an assertion in `label_graph` or `policy_groups` reaches `stopping_on_failure`. Fix: catch,
log, and store the tree with an empty summary.

**m9. Check the GPU headroom at wake on the node.** After parking, the trainer keeps its CUDA context, NCCL buffers and
cuBLAS workspaces on every GPU. A wake needs 0.9 × 24 GiB back, leaving about 2.4 GiB for all of it. One stray CUDA
context on GPU 0 from a rank (~0.3–0.5 GiB each) would make that GPU's wake fail. In the smoke cycle,
`nvidia-smi --query-compute-apps=pid,gpu_uuid,used_memory --format=csv` after the first park should show each rank on
its own GPU only, at no more than about 1 GiB.

**m10. Stale handoffs can fill the tmpfs.** If the loop crashes after the record but before `rmtree` (`loop.py:1138`),
or takes the non-handoff path with a partial handoff, 9.4–14 GB stay in `/dev/shm` until the next durable record. With
the documented 32 GB `--shm-size`, a value phase's handoff then no longer fits. Fix: clear handoff directories whose
adapter is not the phase being published, at the start of `publish`.

## What holds up

- **Trigger matches the trainer.** At μ = 0, `tree_summary.trainable_groups` uses the trainer's own
  `policy_groups` / `has_signal`. μ cannot change whether a group at a proof-graph node has a signal. At 45 minutes
  the trigger will rarely bind (an estimated ~400 groups), which the README already anticipates.
- **Handoff ordering.** The version is served from tmpfs, recorded only after the copy and the rename, and pruned
  only after the record. All three restart windows end in a consistent state.
- **Resident models.** One shared mapping for all ranks, the base never written, merges only in the unparked copy.
  The CPU equivalence tests (`test_resident_trainer.py`) cover two phases and a value phase.
- **Value-arm statistics.** The exact one-sided McNemar test and the conditional Clopper–Pearson interval are computed
  correctly (`evaluation.py`, `paired_difference`).
- **Early resume.** It happens only when no evaluation is due, so it never overlaps the held-out check or the probe.
  Sampling seconds carry over correctly through `sampling_since`.
