# Review J (design): evaluations beside sampling (commit c34e2d0)

Scope: `git show c34e2d0` (probe and miniF2F with the published value model, beside sampling at 56 + 56; held-out
states still at the pause; value arm off), read against DESIGN.md ("Benchmark and value trends", "Fixed targets"),
`src/lean_search/rl/README.md`, `loop.toml`, `loop_smoke.toml`, `deployment/README.md` ("GRPO loop") and the code
paths the commit touches (`loop.py`, `loop_services.py`, `host_memory.py`, `evaluation.py`, `lean/pool.py`). Nothing was
run. Durations below are estimates, not measurements. They come from the naming A/B's per-search percentiles (p90 16 min,
p99 38 min at 112 probe searches). A lognormal fit to those percentiles gives a median of ~5.5 min, a mean of ~7.5 min
and P(> 30 min) ≈ 2%, which is about 3-4 capped searches per 167-problem part.

## Summary answers

1. **Goal and validity.** The design moves in the right direction: the evaluations' Lean-bound tails no longer pause
   every search. The goal of no idle GPUs is only partly met, because the 56/56 split is static. For the whole
   evaluation, its tail included, the loop runs half the searches it was sized for (issue 3).
   - The probe now measures the deployed system (current policy + current value model) at 16 expansions. Its
     difference to version 0's runs stays interpretable as a whole-system trend, because v0's baseline is v0 policy
     + v0 value under the same arrangement.
   - What is lost is attribution. Dropping the value arm also removes the only automatic warning about a harmful value
     model (issue 5).
2. **Load interference.** Load affects the results only through the 30-min wall cap. The cap binds for ~2% of
   searches, and no A/B solve came after 30 min, so the bias is ~0.1-0.3 points (estimate). That is well inside the
   ~2-point run-to-run noise. It is small but not zero, and it is asymmetric between version 0's baseline and later
   slots (issue 4).
3. **Host memory.** The risk is not acceptable as configured: 168 live REPLs plus terms the budget does not count reach
   or pass the 0.85 × RAM line. One config change and one small code change make it safe (issue 2).
4. **Phase trigger.** In steady state a slot (~35-50 min beside sampling, estimate) usually ends before the 45-min
   minimum, so pauses slip by minutes. At the start, though, phase 1 is held about **5-8 hours** (estimate). That is
   acceptable only with a cap on the data a phase trains on, or a single-queue baseline (issue 1).
5. **Docs.** Several passages are stale or wrong (issue 11). The worst are the "wall cap is an emergency stop, stops
   should be zero" claims and the evaluation-share estimate.

## Issues, ranked

### 1. (High) The start holds phase 1 for ~5-8 h; phase 1 is then 2-5× a normal phase

At the start, `evaluate_beside_sampling` runs everything in sequence: probe part 0 twice, part 1 twice, part 2 twice,
then miniF2F (244 problems, 64 expansions, 2-h cap), all at 56 REPLs. `watch` makes the first pause wait for all of it.

**Estimate**
- One 167-problem probe run at 56: 167 × ~7.5 min / 56 ≈ 22 min of full occupancy, plus a tail of up to 30 min, so
  ~35-50 min. Six runs come to ~3.5-5 h.
- miniF2F: ~126 problems solved at the first expansion (~1 min each), ~40 later solves (~20 min each) and ~78 unsolved
  searches at 64 expansions (~50 min each). That is ~4,800 search-minutes / 56 ≈ 1.5 h, plus a tail of up to 2 h, so
  ~1.5-3 h.
- Total: ~5-8 h before the first pause. DESIGN.md's 8-13 min per slot ignores the tail: a p90 of 16 min per search
  cannot fit a 1.5-wave run into 13 min. The same holds for its 1-1.5 h for miniF2F, which was estimated at 112.

**Consequences**
- The first update comes ~5-8 h in instead of ~1.5-2 h. That is ~3-5% of a one-week budget spent on version 0. The
  GPUs are not idle, but the time runs at half concurrency.
- Phase 1 collects ~2-5× a normal phase's trees: 5-8 h at 56 searches is ≈ 2.5-4 h at full rate, against 45-90 min.
  With two passes and no step cap in `phase.toml`, phase 1 trains 2-5× the steps the single-step test calibrated
  (66-84 steps per phase). The result is a large first KL jump (alert at 0.5) and a skewed `reference_phases = 2`
  reference for the relative health limits.
- In the training stage every rank holds the phase's policy sequences. The rank term is still unmeasured
  (`rl/README.md`, "Host memory"), and phase 1 multiplies it by 2-5×. The first pause is where a training OOM is most
  likely.

**Recommendations**
- Add a per-phase training cap, for example `training.max_trainable_groups` (~2-3× `min_trainable_groups`, newest
  first or a random subset). The extra trees stay in the store for the value window and the analysis. Any held pause
  needs this, including miniF2F milestones and slow slots.
- Run version 0's six probe runs as one job over one queue: 1,002 searches at 56 with a single tail. That is ~2.5-3 h
  instead of 3.5-5 h.
- Optionally take version 0's miniF2F out of the loop. Run it in bring-up with `grpo_evaluate.py`, after the gate
  benchmark, with version 0 served, and run the milestone miniF2F runs the same way with the loop stopped. Then
  miniF2F has one arrangement throughout and never holds a phase. Its 64 expansions under a 2-h cap make it more
  load-sensitive than the probe anyway. The tail idles the GPUs a handful of times per run, which is cheap.
- State the long phase 1 in `deployment/README.md` step 6 and in the first-hour checks.

### 2. (High) Host memory at 168 REPLs is over budget once the uncounted terms are added

**Terms while an evaluation runs beside sampling** (GiB, against 0.85 × 241 ≈ 205):
- **REPLs.** The pool reuses REPLs and restarts one on release only past `restart_fraction` (0.5) × 2 GiB = 1 GiB, so
  idle REPLs drift between ~0.25 and 1 GiB. That gives a mean of ~0.6 and a p90 of ~0.9; in-flight REPLs can reach
  2 GiB. 168 × 0.6 ≈ 100 GiB realistic; the budget's p90 form gives ≈ 150 GiB.
- **vLLM:** ~25. **Parked trainer in /dev/shm:** 14 (README) to 28 (your figure and the `loop.toml` tmpfs size).
- **Not in any budget condition:**
  - In a value phase, the main rank holds the 4-phase labelled window while sampling. At ~1.4 MiB per tree that is
    ~15 GiB at ~3,000 trees per phase.
  - The four parked ranks' own resident memory (torch, CUDA context, NCCL): unmeasured, plausibly 8-20.
  - The loop process (value benchmark, summaries) and the evaluation job's process: a few each.
- **Total:** ~150-195 GiB realistic, ~200-230 GiB by the budget's own p90 convention plus the uncounted terms. The README
  already notes that a p90 of 1 GiB is over the limit.
- `host_memory.budget_conditions` only logs `OVER`; nothing enforces it. A cgroup OOM kills the largest process, a
  vLLM server or a trainer rank, and takes the loop down.

**Safer setting (concrete)**
- **Config, no code:** add `[lean] restart_fraction = 0.25` to `experiments/configs/grpo/search/visible_student_v2.toml`.
  The evaluation jobs inherit it through the template.
  - Released REPLs then restart at 0.5 GiB or 2,000 proof states, so the idle mean drops to ~0.35-0.4 GiB:
    168 × 0.4 ≈ 65-70 GiB, about 35 GiB less.
  - Cost: a header import every few searches per REPL, a few CPU-seconds, which 122 cores absorb.
- **Small code change:** once an evaluation beside sampling starts, stop the idle REPL processes of the sampling pool
  beyond `concurrency_beside_evaluations`. This needs a `LeanReplPool.stop_idle(keep)` beside `stop_processes`. They
  restart lazily on their next acquire, so ~112 live REPLs remain, as at the pause.
- **Guard:**
  - Count the main rank's labelled window and the parked ranks' resident memory in the sampling and evaluating
    conditions.
  - Before starting an evaluation beside sampling, require `memory_available ≥ evaluation concurrency × 1 GiB + 20 GiB`,
    otherwise defer it to the next pause.
  - Turn `OVER` into an `Alert:` (status counter, dashboard).
- Change these before `init`. Version 0's baseline must run under the arrangement every later slot uses. The resumable
  evaluation directories refuse a changed config, and the REPL counts are part of that config (`keep_config`).

### 3. (High/Medium) The static 56/56 split halves the loop for the whole evaluation, tail included

`work()` keeps workers 56-111 idle for as long as the task runs. During the Lean-bound tail, when only a few probe
searches remain, the GPUs see ~56 searches plus a handful, against the 112 the loop is sized for. The `loop.toml`
comment says "most searches wait on the GPUs"; the 2×3090 measurements needed ~120 searches to fill two GPUs. The
tail's idle time is therefore halved, not removed.

At ~35-50 min per slot every 2 h, this costs up to ~15-25 min of full-rate sampling per slot. That is still less than
the old paused design: probe slot plus value arm, both fully paused, and also tail-bound.

**Recommendations**
- Admit sampling workers up to `sampling.concurrency − evaluation searches in flight`. The loop can derive the in-flight
  count from the evaluation directory's `results.jsonl`: `min(concurrency, problems − finished)`. A cruder version
  releases all workers once the evaluation has no pending problems.
- With that in place, restore `[evaluation.probe] max_wall_seconds = 3600`. Commit 8133bbe lowered it to 1800 because
  the tail idled the paused loop's GPUs. Beside sampling with dynamic admission a long tail costs almost nothing, and
  "the expansions are the budget" holds again.
- Measure policy samples/s and GPU utilization during an evaluation beside sampling versus without one, first hour and
  smoke cycle. This settles whether 56 searches alone saturate the GPUs.

### 4. (Medium) The probe is load-dependent through the wall cap, and the load profile differs from version 0's

- **Magnitude.** About 2% of searches pass 30 min (≈ 3-4 per part), and the A/B had no solve after 30 min. A 20% load
  stretch would cut the ~1.3% of searches that finish between 25 and 30 min, of which few solve. The bias is ~0.1-0.3
  points, against ~2 points of run-to-run noise.
- **Load drift over the run.** The sampling load changes as the run goes on:
  - The curriculum band rises, so sampling searches spend more Lean time.
  - RL may lengthen the policy's outputs, so GPU latency rises for both the probe and sampling.
  - The value benchmark scoring starts at the same moment as the slot.
- **Asymmetry.** At the start the evaluation launches before any worker, so version 0's runs see 56 + 56 throughout. A
  later slot starts right after a resume, when all 112 paused searches continue (and replay their stopped REPLs) beside
  the 56 evaluation searches. That is 168 in flight plus a CPU burst of REPL restarts and 56 Mathlib imports.

**Recommendations**
- Report per slot `wall_clock_stops` and the expansions the stopped searches reached; a stop at 16 expansions is
  harmless. Alert when the stops exceed twice version 0's.
- Restore the 3,600-s cap (issue 3).
- Optionally start the evaluation job a few minutes after the resume, or once the in-flight count falls to the admitted
  level, so that both arrangements are 56 + 56.

### 5. (Medium) No automatic warning about a harmful value model; probe attribution is lost

**What the probe still measures**
- The probe is now a whole-system metric: the policy, plus a value model that lags it by up to 2 phases and was trained
  on its last 4 phases' trees.
- The trend against version 0 is valid as "is the deployed search better than at the start". Each slot records
  `(policy, value)` versions, so the dashboard can mark value switches.
- A value retrain lands every 2 phases while slots come every ~2 h (1-1.5 phases). Consecutive slots therefore switch
  value models irregularly, and the 3-slot rolling mean mixes 2-3 value models. That adds variance the version-0 noise
  estimate does not contain.

**What was lost by dropping the value arm**
- The arm was weak: one arm found a 5-point harm about a quarter of the time.
- It was still the only search-level, on-distribution check of a value model, and the only automatic value alert. With
  `enabled = false`, `loop.py` has no path left that alerts on a worse value model:
  - The benchmark trend alerts only on errors.
  - The benchmark comes from gate-set trees searched by the starting policy without a value model. As the policy
    drifts, it measures ranking on increasingly off-distribution states.
  - The free `value_phase` calibration is on-distribution, but it is computed on trees that value model itself guided.
- The rollback is policy-only, so a value regression can lower the probe with nothing to tell policy from value. Every
  value model is published (no gate), so a bad one drives sampling for 2 phases.

**Cheap mitigations**
- Free: raise an `Alert:` when the benchmark's paired bootstrap interval for pair accuracy against v0 lies wholly below
  0, or its AUC falls by more than a set margin. Require two consecutive value models to limit false alarms.
- Cheap, beside sampling, no swap:
  - Once per published value model (or daily), search the slot's part again with **no value model** (log-probability
    best-first, as the gate search does), paired per problem with the slot's run.
  - The no-value arm gives the policy-alone trend, and the paired difference gives the value model's contribution in
    search. Neither needs the value servers.
  - It needs a version-0 no-value run of each part at the start (3 more runs, or one part only).
  - It replaces the v0-value arm without the swap the commit removed.

### 6. (Medium) An evaluation failure beside sampling stops the loop, and server recovery now provokes one

- `search_problem_set` gathers without handling `httpx.HTTPError`, so one failed request fails the job.
  `stopping_on_failure` then stops the loop.
- `recover_servers` restarts servers that do not answer *while the evaluation runs* ("its requests to them fail
  either way"). A recovery that saves sampling therefore kills the loop whenever a slot is running, which is ~30-40% of
  the wall time.
- Before this commit no recovery could overlap an evaluation: the evaluation ran at the pause, under the pause lock.
- An evaluation is measurement. Its failure should not stop training.

**Recommendations**
- Treat a failed evaluation beside sampling like the value benchmark scoring: log an `Alert:`, do not mark it, and retry
  it after the next pause. The resumable directory keeps the finished problems, and the slot number is not consumed.
- Alternatively, requeue a problem on `HTTPError` inside the job, as `search_service.work` does.
- Add a job-level timeout (for example 2 h for a probe slot, 5 h for miniF2F) after which the job is cancelled with an
  alert and the pause proceeds. A hang outside the per-search cap (a REPL start, a stalled server) can otherwise hold the
  phase indefinitely while sampling runs at half concurrency.

### 7. (Medium) The phase trigger's maximum is now soft, and the cost is invisible in the phase records

- `max_sampling_minutes = 90` is no longer a maximum.
  - A miniF2F milestone (~1.5-3 h at 56) holds its phase that long.
  - A slow slot delays the pause by its overrun.
  - In steady state the effect is small: a slot starts at the resume and the minimum is 45 min.
- Phases that contain a slot gain trainable groups more slowly for part of their time. Phase lengths and trees per
  phase alternate with the slot rhythm.
- `phases.jsonl` and the `timing` line record only the evaluations at the pause. The real cost of an evaluation beside
  sampling (minutes at reduced concurrency) appears only as a `loop.log` line, and `status` says `searching`
  throughout.

**Recommendations**
- Add `beside_evaluation_seconds` (and the kinds) to `PhaseRecord`/`PhaseTiming`, plus the samples/s during and
  outside the evaluation.
- Add a status flag such as `evaluating_beside_sampling` so the dashboard shows why a due phase waits.
- Note in the trigger paragraph of `rl/README.md` and in `loop.toml` `[training]` that the maximum yields to an
  evaluation in flight.
- The per-phase training cap of issue 1 also bounds the effect of these held phases.

### 8. (Low/Medium) The smoke cycle no longer fits its hour, and the swap path is now untested

- `loop_smoke.toml` keeps `max_wall_seconds = 3600` for the probe and 7200 for miniF2F (8 problems at 64 expansions).
- Phase 1 waits for 6 sequential 4-problem runs (each as long as its slowest search, ~10-15 min, up to 60) and then
  miniF2F. That is ~1.5-2 h before the first 5-10-min phase can pause.
- Every later phase waits for its slot (`every_hours = 0.01`). "About an hour" for two phases does not hold.
- With `value_model = "published"` everywhere, nothing on the node exercises the v0 swap (`kept_value_weights`,
  `serve_value`) or the value arm any more, yet the code paths remain.

**Recommendations**
- Smoke settings: probe `max_wall_seconds = 600`, miniF2F `problems = 4` with `max_wall_seconds = 900`. Optionally
  probe `problems = 6` (2 per part).
- State in `rl/README.md` that `value_model = "initial"` and the value arm are untested on GPU since 2026-10-30, or
  remove them.

### 9. (Low) `watch` blocks for the whole wait

`await self.finish_evaluations_beside_sampling()` sits inside `watch`. While it waits, potentially hours at the start,
nothing saves progress (`sampling_seconds`) and no curriculum messages or newly verified statements are read
(`statements.refresh`). A crash in that window loses the phase's sampling time and makes the restart's `phase_due`
wrong.

**Recommendation:** wait with a timeout of `check_seconds` in the loop, and keep refreshing and saving meanwhile.

### 10. (Low) Config validation

`parse_loop_config` accepts any `concurrency_beside_evaluations`. A value of 0 stops sampling for the whole evaluation;
a value above `concurrency` is meaningless.

**Recommendation:** require `1 ≤ concurrency_beside_evaluations ≤ concurrency` (a user-input boundary: `ValueError`).

## Verdict

The decision is sound and is a net improvement. Evaluating the deployed system with the published value model is a
defensible primary metric, and the tails no longer pause every search. Version 0's baseline uses the same arrangement,
so the trend stays internally consistent. The wall cap's load-dependence is far below the run-to-run noise.

Four things should change before the loop starts:
1. Cut the REPL memory: `restart_fraction = 0.25` and/or stop idle REPLs during an evaluation, plus a memory guard.
2. Make a failed or hung evaluation beside sampling an alert with a retry, not a loop stop.
3. Bound what a held phase trains on, and shorten the start (a single-queue baseline; optionally miniF2F outside the
   loop). Phase 1 should not be a 5-8-h, 2-5× outsized first update.
4. Add a free benchmark-based value alert in place of the dropped arm.

Dynamic admission with the 3,600-s cap restored would finish the job of not idling the GPUs. A swap-free no-value
probe arm would restore attribution cheaply. The docs need the listed corrections, the wall-cap "emergency stop"
claims first.
