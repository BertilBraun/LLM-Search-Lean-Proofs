# Review F: search-tree GRPO loop, readiness to rent (master 8e9a157, 2026-10-29)

## Verdict: conditional go

The stage machine, the restart logic, the credit rules and the data-parallel trainer are careful and well tested: the
561 non-Lean tests in `tests/rl` and `tests/graph` pass in WSL (2 min 12 s). Five things should still be fixed before
renting, each under a day locally:

1. A GPU memory leak between the training job's stages (verified). It will likely crash value phases and merges.
2. The curriculum's solve-rate controller is biased by search duration. A simulation of the actual rule drifts to a
   17–21% solve rate instead of 30–70%.
3. A dead vLLM server stalls the loop silently.
4. Parsing the value window's trees is slow (measured) and adds about 10 min to every fourth pause.
5. The first-day order runs about 2 h of baseline evaluations before any training stage has been tried.

The learning signal is coherent but thin per GPU-hour. Expect a small, slow policy change, which the probe detects only
above about 3 points.

## What I verified and how

- Tests: `pytest tests/rl tests/graph` without the two Lean files: 561 passed.
- Compile reference cycle (`scratchpad/review_f/compile_cycle.py`): after `nn.Module.compile()` a module's weight
  survives until `gc.collect()`; without compile it is freed at once.
- Curriculum bias (`scratchpad/review_f/curriculum_sim.py`): an event simulation of `Curriculum.record_outcome` (window
  50, generation reset, raise 0.5/0.8, lower 0.3) with 112 concurrent searches.
- Tree parsing (`scratchpad/review_f/convert_speed.py`): `from_json_object` takes 1.93 µs per token value; `json.loads`
  of the same data takes 0.05 s.
- Throughput and cost come from measurements in the repo, marked "estimate" where extrapolated: the 4B at a 0.62 share
  generates about 1,900 tokens/s per GPU with about 80 running sequences (`results/phase5_teacher_student`); a visible
  sample is about 300 tokens (`results/phase5_visible_series`: 93,685 tokens / 19.8 expansions / 16 samples).

## Findings

### B1 (blocker, cheap fix): the policy model stays on the GPU through the value stage and the merges

`training/sft.py:367-370` compiles the `mlp`, every projection and the norms with `module.compile()`, which stores
`torch.compile(self._call_impl)` on the module. The module then refers to itself and is freed only by the cyclic garbage
collector, not when its last reference goes (verified on the CPU above).

`run_training_phase` (`rl/training_phase.py:329,350`) calls only `torch.cuda.empty_cache()`, which cannot free live
tensors, and a full gen-2 collection is unlikely in a process holding millions of tree objects. So the policy's ~9.4 GiB
of bf16 weights plus its ~0.5 GiB fp32 LoRA likely stay on every rank while the value model trains (2B, 32k-token
micro-batches), rank 0 runs the gate (two adapters scored) and `merge_on_gpus` loads another 4B base on rank 0
(9.4 GiB).

With the sleeping servers' ~1.6 GiB already on each 24 GiB card, the value phase (phase 4, about 3 h in) is
near-certain to run out of memory (~25 GiB); a plain phase's merge sits at about 21–22 GiB. The out-of-memory stops the
loop, and the restart reruns the same stage.

Fix: after each stage, `del` module, scorer and optimizer, then `gc.collect()` and `empty_cache()` (better, return
nothing that references the model from `train_grpo` and `train_graph_value_model`). Log `torch.cuda.memory_allocated()`
before the value stage and the merge, and report peak memory for those stages too; `peak_memory_gib` covers only policy
training, reset after scoring (`policy_trainer.py:500`).

### M1 (major, verified by simulation): the curriculum drifts to a ~20% solve rate

`Curriculum.record_outcome` (`expert_iteration/curriculum.py:208-226`) moves the band on the first 50 *outcomes* of the
current generation, and with 112 searches in flight outcomes arrive in order of duration. A solved tree finishes in
about 1–12 min (first proof, then up to 16 harvest expansions). An unsolved tree runs 64 expansions at about 35 s each,
about 37 min (estimate: 11.5k expansions/h shared by 112 searches). So the first 50 outcomes after every move are mostly
solved, and the band rises fast (+1.5 at 80%) until even this fast-arriving sample falls under 50%.

| Solved / unsolved duration | Simulated realized solve rate |
|---|---|
| 1–12 / 30–50 min | 0.17 |
| 1–12 / 12–25 min | 0.21 |
| equal durations (control case) | 0.40 |

Consequences: about 80% of trees are unsolved, cost most of the compute and give no policy groups. Solved trees per
30-min phase fall to about 20 (estimate), so phases end on `max_sampling_minutes` with about 80 groups and about 10 steps
per pass. The `solve_rate_off_target` alert will fire with no obvious cause.

Fix: judge a generation by the first N statements *fed* in it, once all N have finished, rather than by the first N
outcomes (or track in-flight statements as pending). The same bias affects `loop_overfit.toml` (m5).

### M2 (major, operational): one dead vLLM server stops all useful work without stopping the loop

The policy client cycles over all servers (`policy/expander.py:188`), so with one of four down nearly every search hits
it. `work` and `server_failed` (`rl/loop.py:514-559`) retry each statement 3 times, then drop it; `abandon` is a no-op,
so the statement is lost until a restart. Nothing pauses or stops the loop, and `phase_due` needs a solved tree, so no
phase starts: hours of idle GPUs overnight, with only a passive dashboard alert.

Fix: after K consecutive failures (or a failure rate above a threshold), pause the gate and probe `/health`. Take a dead
server out of rotation or try `serve_model.sh` once; failing that, exit non-zero so an outer watchdog (cron or a `while`
loop around `grpo_loop.py run`) restarts servers and loop. Also start `grpo_loop.sh servers` on the four GPUs in
parallel; it is serial now (8 × 1.5–4.6 min, about 12–37 min).

### M3 (major, measured): reading the value window's trees takes about 10 min per rank

`read_tree` sends every number through `_convert` with typing introspection and per-element f-strings
(`records.py:113-139`): 1.93 µs per value, about 0.6 s for one unsolved tree's tokens alone. `value_records`
(`experiments/grpo_phase.py:68`) fully parses 8 phases' records (about 2,000 trees) on *each* of the 4 ranks, then drops
the texts: about 10–15 min per value phase, hidden in `trainer_start`. Ordinary phases pay about 1–2 min per rank, and
the loop process parses the same trees again for its metrics (`loop.py:685`).

Fix: `json.load`, delete `expansions` from the dict before `from_json_object` for window trees, and fast-path tuples of
primitives in `_convert`. Optionally parse once on rank 0 and broadcast, or cache the stripped records per phase.

### M4 (major, cost): fixed pause costs dominate small phases; about a quarter of GPU time is pause

Estimate at a 50% solve rate: about 11.5k expansions/h on 4 GPUs (4 × 1,900 tokens/s ÷ about 2,400 tokens per n = 8
expansion), about 200–280 trees/h, and per 30-min phase about 65 solved trees, 270 groups and 1.9k sequences. That is
about 30 steps per pass, 1–3 GPU-minutes of compute on four GPUs.

The fixed parts paid every phase (trainer start and tree parsing, 4B load on four ranks, compile, reference scoring, the
merge plus a 9.4 GB write, the wakes) come to about 5–8 min. So GPUs sample about 75–80% of wall time, about 70% of each
pause is overhead, and only about 4% of generated samples are trained on, since groups exist only at proof-graph nodes
of solved trees. About 75% of expansions go to unsolved trees, which yield value targets only (worse under M1).

With lr 1e-5 and the clip almost never binding, staleness is not a concern. Levers:
1. `min_sampling_minutes = 45`, `max_sampling_minutes = 90`, and trigger on trained groups (≥ 300) rather than solved
   trees (review D's "tiny phases" point is still open).
2. `max_expansions` 32 instead of 64 in the loop's search config; the probe measures at 16 anyway, and in the visible run
   expansions 17–64 added 8 of 171 solves (`results/phase5_visible_series`).
3. Skip reference scoring (`policy_trainer.py:480`): with `kl_coefficient = 0` it is only reported, at about 10% of
   training compute. Score a 10% subsample instead.

### M5 (major, measurement): value A/B (b) is close to a coin flip and nothing reverts a worse model

`value_ab_result` (`rl/evaluation.py:208`) passes when the published model solves ≥ 1 more problem and reference is not
significantly better, which happens about 45% of the time with no real difference. Gate (a) admits a no-gain model 2–4%
of the time per retrain (DESIGN), so over 30+ retrains a false pass is more likely than not. μ = 0.15 then switches on,
permanently, with roughly 25–30% probability on a model no better than v0. And an A/B that finds the published model
*worse* (`worse_p_value < 0.05`) changes nothing: training searches keep using it.

Fix: require one-sided `better` p < 0.1 (or a ≥ 2√discordant lead) to turn μ on. Revert the published value model to v0
(or the last A/B-passed one) when the A/B finds it worse. Skip the A/B when neither the value model nor μ changed since
the last one; it costs about 45 min per 12 h, about 6% of the run.

### M6 (major, plausible): host RAM during the training stage is outside the budget

The README's budget ("Host memory") covers publishing and evaluating, not training. During training, all 112 paused
REPLs stay alive (`release_lean_memory` runs only before evaluations, `loop.py:813`), next to 8 sleeping vLLM processes,
4 ranks each holding the whole phase's parsed trees (about 1–2 GB of Python objects per rank, estimated from M3's token
counts; more in value phases) and the loop process parsing the same trees again. An OOM kill of a vLLM process during
training would surface only at wake.

Fix: stop the paused REPLs before training as well (they replay anyway), and let only rank 0 build the policy data and
broadcast the sequences. Measure during the first training stage, as the checklist says.

### M7 (major, operational): disk grows without bound and is not monitored

Per phase: a 496 MB fp32 policy adapter (measured on the node backup's 4B adapters), about 150–250 MB of gzipped trees
(estimate: about 0.9 MB of tokens per unsolved tree), and a 257 MB value adapter every 4 phases. `MergedPublisher.prune`
deletes only merged weights, so 150–200 phases add about 100–150 GB on top of the HF cache (4B, 2B, the 9B teacher),
Mathlib, the datasets, the SFT checkpoints and about 27 GB of merged weights. A full disk fails `write_json_atomically`
or the 9.4 GB merge write and stops the loop, and `monitoring/` has no disk metric or alert.

Fix: rent ≥ 500 GB, add `shutil.disk_usage` to `record-system` with an alert, and prune old phase adapters (keep every
10th plus the last 3).

### M8 (major, process): the bring-up order tests training last

`grpo_loop.sh loop` first runs two probe runs and the held-out states (about 1.5–2 h), then samples for up to 30 min.
The first pause (NCCL setup, rank memory, merges, wake) comes about 2.5–3 h after starting, the first value phase (phase
4, B1) 2–3 h after that. Missing from the checklist:

- (a) A smoke cycle before any baseline: `LOOP_CONFIG=loop_overfit.toml` with `min_sampling_minutes = 5`,
  `min_solved_trees = 10` and, for one run, `value_every_phases = 1` plus a benchmark, so one policy+value phase with
  both merges and the wake runs in the first hour.
- (b) A 4-rank NCCL all-reduce test (`torchrun --nproc-per-node 4`) with `nvidia-smi topo -m` and `df -h /dev/shm`.
  Docker's 64 MB `/dev/shm` breaks NCCL's SHM transport; P2P is usually unavailable on 3090s.
- (c) The vLLM start logs' KV cache GiB and maximum concurrency at the 0.62 share, and `vllm:num_preemptions_total`
  under load.
- (d) `request-evaluation --target minif2f` *before* the first `loop`. `grpo_evaluate.py` evaluates only the current
  version (`grpo_evaluate.py:90`) and `prune` deletes v0's merged policy after v1, so a forgotten baseline needs a manual
  re-merge.
- (e) Disk free and its projection (M7).
- (f) After about 2 h of sampling, the realized solve rate against the band (M1).
- (g) Expansions/h, trees/h and trained groups per phase, to set the phase length (M4).

### Minor

- m1. `BACKGROUND_CPUS` pins the whole loop process to the background CPUs at nice 19 (`grpo_loop.sh` `loop`): the
  asyncio orchestrator (a GPU feeder by the README's own rule), the torchrun ranks and the evaluation jobs. The old
  trainer explicitly unpinned its ranks (`expert_iteration/trainer.py:739`). Leave it unset without a cgroup quota, or
  unpin training via `command_prefix = "taskset --cpu-list 0-N"`.
- m2. `grpo_loop.sh stop` kills all servers right after SIGTERM, so every restart costs a full serial server bring-up
  (M2). Split it into `stop` (loop only) and `stop-servers`.
- m3. Each phase uses a fresh AdamW with 5 warmup steps (`phase.toml`). With 10–30 steps per pass, 15–25% of each
  phase's steps run at reduced lr on single-gradient moments. Persist the optimizer state with the adapter (~1 GB), or
  warm up only in phase 1.
- m4. `mean_ratio` and `kl_to_data_policy` average over all trained tokens, so whether pass 1 raised positive-advantage
  tokens and lowered negative ones is not logged. Add the second pass's mean (ratio − 1) split by advantage sign: the
  earliest "is the update going the right way" signal.
- m5. The overfit `report` (`grpo_loop.py`) computes solved / trees per phase. Phase 1 is dominated by fast solved trees
  (unsolved ones spill into phase 2), and `FixedStatements` re-feeds fast statements more often, so the per-phase rate
  is throughput-weighted. Report each statement's outcome by its k-th search instead.
- m6. Any non-HTTP exception in one of 112 searches stops the whole loop (`loop.py:530-532`, `stopping_on_failure`),
  which over days is likely at least once. Contain it per search (log, count, abandon) up to a rate limit.
- m7. After a restart in TRAINING, `steps.jsonl` is appended again, duplicating step records on the dashboard.
- m8. Probe strata: if v0's hard stratum is near 0% or its easy stratum near 100% at 16 expansions, a third of the
  probe carries no information. Check v0's per-stratum rates and re-select if needed.

## Learning signal (question 3)

The credit is coherent: a block's tactic advantages sum to score − b, stopping is neutral, no-ops count as failures, and
I found no exploit in `grpo_groups.py`, `advantages.py` or `token_credit.py`. In practice the trained contrast is
"tactics on a found proof" (+0.85, plus 0.2 per step) against "first tactic fails or is a no-op" (−0.15), with about 20%
of group tactics neutral: expert iteration plus Lean-error negatives, which should move the policy.

The question is how fast. About 10–30 steps per pass at lr 1e-5 with Adam (the low end for LoRA RL) leave the clip almost
never binding, so 2 passes amount to about 2× vanilla policy-gradient steps, not PPO. Expect a KL to the starting
weights of order 1e-4–1e-3 per token after the first 5–10 phases.

Signs within the first day that it is not moving:
- `kl_to_reference` per token stays below ~1e-4 after 5 phases, or stops rising;
- the sign-split ratio of m4 shows less than 1% movement in pass 2;
- `gradient_norm` is pinned at the 1.0 clip, so the effective lr is lower still;
- the policy-sample failure rate per difficulty band (not overall, because of M1) is flat over 6–8 phases;
- the held-out-states per-sample success at 6 h is flat (standard error about 1.5–2 points).

If the first three hold, raise lr to 3e-5 (cheap to try in the single-step test first). Either way, run the single-step
test with both credits before the loop: it is the only experiment that isolates "does a phase improve the states it
trained on".

## Measurement validity (question 4)

- The probe (501 problems, 16 expansions, v0 value fixed, wall cap as an emergency stop) is a sound in-distribution
  policy measure. Version 0's two runs give one estimate of the discordance D; differences under about 2√D (likely
  ±12–15 problems, 2.5–3 points) are noise.
- miniF2F-valid (±5–7 theorems) will not resolve an RL gain of this size; treat it as a regression check.
- With no control run, a probe gain cannot be split into "RL credit" and "more SFT-like data on own proofs"; the
  single-step per-tactic vs sequence comparison is the only credit ablation.
- The value side cannot answer "did the value model help" as specified (M5). Gate (a), with 50–80 pairs, is a weak
  pre-filter; adopting DESIGN's option (ii), the A/B as the decision, plus M5's fixes, is the defensible choice.

## Cost (question 2)

$200 at about $0.80/h is about 250 h. Rebuild, the SFT stage, the naming A/B, the gate search and the single-step and
overfit tests take roughly 25–35 h, leaving about 200 h for the loop (about 130 h at $1.20/h).

Once a value model is published, evaluations take about 17% of wall time: probe and held-out states about 50 min every 6
loop-hours, the value A/B about 45 min every 12 h. That is affordable; trimming the A/B (M5) and probing every 8 h brings
it to about 10%. The larger cost is M1 plus M4 (unsolved-tree compute and pause overhead), not evaluations.

   (strip `expansions` before conversion) and M2 (pause or stop on failures, parallel server starts). Add a disk metric
   (M7) and the sign-split ratio metric (m4), set phase length and trigger (M4), and add a regression test of the
   curriculum against duration-biased outcomes.

   `nvidia-smi topo -m`, a 4-rank NCCL all-reduce, HF and GitHub reachability.
2. Rebuild, then the heartbeat replay, which fixes the caps every later search uses.
3. `init`, `servers`, `check`. Record KV cache GiB, concurrency and the start time per server.
4. Smoke cycle on `loop_overfit.toml` with short phases and one forced value phase. Check every pause segment,
   `peak_memory_gib` per stage, `nvidia-smi` during training and merge, host `memory_available` during training, the
   wake, `mean_ratio` 1 and `clip_fraction` 0 on step 1, the sampler difference (processed mode), and that `v0001`'s
   weights differ from `v0000`'s.
5. Single-step GRPO with both credit arms (about 2 GPU-hours): go or no-go on the learning rate.
6. SFT stage, naming A/B, gate benchmark (as planned).
7. Fresh `init` of the main loop, then `request-evaluation --target minif2f`, then `loop` (two probes, held-out states,
   miniF2F at v0).
8. In the first 6 h of the main loop, check the realized solve rate against the band, trained groups per phase, the
   pause share of wall time, disk growth per phase and the `kl_to_reference` trend.

   stay comparable.
