## Findings, by severity

### 1. (High, blocker) Version 0's probe baseline crashes when slot 2 finishes before slot 0 or 1, and a restart can never get past it

**Where.** `experiments/grpo_evaluate.py:145-147` and `:157-163` (`last_slots`), `src/lean_search/rl/loop.py:607-621`
(`slot_baseline_difference`, `probe_baseline_differences`), `loop.py:417-420` (`probe_slot_directory`).

**Scenario.**
- `run_baselines` now starts all six probe jobs at once (slots 0-2, two runs each), plus miniF2F and the held-out
  states.
- `grpo_evaluate.py` creates each run directory when the job starts (`directory.mkdir`, line 123).
- The first run of a slot computes `last_slots` and `probe_baseline_differences` for that slot. These cover the slots
  `slot - probe_parts + 1 .. slot`; for slot 2 that is slots 0, 1 and 2.
- `probe_slot_directory(n)` returns any directory that matches `probe_slot000n_v####`, whether or not it holds a summary.
  Both functions then call `read_summary(directory / "summary.json")`.
- If slot 2's first run finishes while slot 0's or slot 1's first run is still searching, that directory exists but has
  no `summary.json`. The read raises `FileNotFoundError`.
  - This happens after the job wrote its own summary.json and its repeat comparisons, so the job exits nonzero.
  - `run_logged` raises, the `TaskGroup` in `run_baselines` cancels the other seven jobs, and the session stops on the
    failure.
- The first three runs take similar time, so this happens with a probability of about 2/3.
- **A restart cannot get past it.**
  - Slot 2's directory is now complete, so its job has nothing to search. It reaches `last_slots` within seconds and
    crashes again.
  - The crash cancels slots 0 and 1 before they have even loaded their REPL headers.
  - Every restart repeats this, so the loop can no longer pass version 0's baseline without manual work.
- `loop_smoke.toml` has the same layout (3 parts, `baseline_runs = 2`, `at_start = true`), so the smoke cycle is hit
  too.

**Reproduction.**
- The script creates the six v0 slot directories, with summaries only for slots 1 and 2.
- Both functions raise:
  ```
  probe_baseline_differences raised FileNotFoundError ... probe_slot0000_v0000/summary.json
  grpo_evaluate.last_slots raised FileNotFoundError ... probe_slot0000_v0000/summary.json
  ```

**Why the tests miss it.** `FakeEvaluations` never runs `grpo_evaluate.py`'s post-processing, so
`test_version_zeros_baseline_runs_all_at_once` and the other baseline tests pass whatever the jobs would do.

**Fix.**
- Make `probe_slot_directory` consider only directories that hold a `summary.json`, for example by globbing
  `probe_slot{slot:04d}_v[0-9][0-9][0-9][0-9]/summary.json` and returning the parent.
- `last_slots` then returns None and `slot_baseline_difference` returns None for a slot still running.
- To keep version 0's rolling probe line, write it once after the baselines in `run_baselines`, or by whichever first
  run finishes last, as the repeat comparisons already do.
- Add a test that runs `grpo_evaluate.evaluate`'s post-processing, or at least `last_slots` and
  `probe_baseline_differences`, with a slot directory that has no summary.

**Confidence.** High. The crash is reproduced. The no-way-past-it outcome on restart follows from the code paths;
I have not run it on the node.

### 2. (Medium) In an evaluation's tail the node runs up to ~165 REPL processes; the budget and the README say 112

**Where.** `src/lean_search/rl/loop_services.py:699-715` (`evaluation_repls`), `loop.py:1452-1460`
(`sampling_limit`), `src/lean_search/rl/evaluation.py:505-522` (the evaluation job's pool), and `rl/README.md` around
line 571.

**Scenario.**
- `sampling_limit` subtracts the job's *searches in flight*, `min(unfinished, concurrency)`.
- The job's own `LeanReplPool` keeps all of its `pool_size` (56) REPL processes alive until the job ends. Idle ones are
  never stopped.
- In the probe's Lean-bound tail, with say 3 problems unfinished, sampling refills to 109 searches. The node then holds
  109 + 56 ≈ 165 live REPL processes.
- With the 3600 s caps this tail can last up to an hour.
- This is review J's #2 (168 REPLs) again, now only in the tail. But `evaluation_repls` now reports
  `max(112, 56 + 56) = 112`. The test `test_beside_sampling_the_evaluation_repls_stay_within_the_sampling_concurrency`
  fixes that understatement in place, and the README tells the operator the same.
- At a p90 of about 0.9 GiB per idle REPL (review J's estimate), 165 REPLs plus vLLM plus the parked trainer exceed
  0.85 × RAM.

**Fix.**
- In `search_problem_set`'s `on_completed`, once `unfinished < concurrency` (every remaining problem is already in
  flight), call `await pool.stop_idle_processes(unfinished)`. Those REPLs can never be needed again in that job.
- Alternatively, report the job's running REPL processes in `progress.json` and subtract those in `sampling_limit`.
- Either way, `evaluation_repls` and the README must state the true peak.

**Confidence.** High that the count is understated. Medium that it reaches OOM; that depends on the measured REPL p90.

### 3. (Medium) A probe slot cut off at the pause starts again from zero, so a slot that never fits never completes

**Where.** `loop.py:936-952` (`watch`), `loop.py:1559-1568` (`run_probe`), `loop.py:411-415`
(`evaluation_directory`, which is per version), and `loop.toml` (`probe.max_wall_seconds = 3600`).

**Scenario.**
- The probe slot starts right after a pause. The next phase is due after 45-90 min of sampling, plus at most 30 min of
  wait, so the slot has about 75-120 min.
- A probe part (~167 problems at 56 concurrency) runs about three waves. A problem in the last wave that runs into the
  3600 s cap pushes the slot past 75 min.
- When `watch` cancels the slot, the retry runs after the pause, at the new version. That is a new directory, so
  everything already searched is discarded.
- If a part's runtime regularly exceeds the shortest phase plus 30 min, that slot is cut off every phase:
  - the probe never advances;
  - each phase waits the full 30 min;
  - `evaluation_failures` keeps climbing.
- Nothing escalates this beyond the per-session counter.

**Fix.**
- Quick: keep `probe.max_wall_seconds` well below `min_sampling_minutes + max_pause_wait_minutes` minus the earlier
  waves, for example 1800 s as in 8133bbe, now that the tail no longer idles the GPUs.
- Proper: at the wait's end, signal the job to stop its searches on the wall clock (a deadline file it polls) rather
  than cancelling it. The slot then completes with the stops reported.
- Also: after a second consecutive cut-off of the same slot, raise an `Alert:` or run that slot at the pause.

**Confidence.** Medium. The mechanism is certain; how often it happens depends on the probe's real tail.

### 4. (Medium, conditional blocker) A version 0 baseline left half-done by the earlier code cannot be resumed

**Where.** `src/lean_search/rl/evaluation.py:470-475` (`keep_config`), `fixed_targets.py:59-75`
(`baseline_concurrency`, `run_target`), and `loop.py:1634-1645` (`baseline_runs`).

**Scenario.**
- Under c34e2d0 and earlier, the baseline ran at each target's own concurrency: probe 56, miniF2F 56, held-out 112.
- Suppose a loop on the node started that baseline and was stopped mid-run. One example is `probe_slot0001_v0000` with
  some `results.jsonl` lines; another is `minif2f_v0000` begun but incomplete.
- The new code resumes those directories with `--concurrency 11/40/6`. `lean.concurrency` and `pool_size` are part of
  `config.toml`, so `keep_config` raises "holds another config".
- The job exits nonzero, the `TaskGroup` cancels the rest, and the loop stops at start, again on every restart.
- The same happens if someone edits `baseline_concurrency` or `sampling.concurrency` (the equal-share fallback) while a
  baseline is unfinished.

**Fix.**
- Before starting on the node, check `$LEAN_SEARCH_RUNS/<loop>/evaluations/*_v0000*` for directories without
  `summary.json`. Delete them, or start a fresh loop name.
- Optionally, in `run_baselines`, compare each run directory's `config.toml` with the config about to be used and fail
  with an actionable message before starting any job.

**Confidence.** High if such a directory exists; it does not matter for a fresh `init`.

### 5. (Low) Concurrent sibling jobs read summary.json files that are not written atomically

**Where.** `evaluation.py:551` (`paths.summary.write_text`), `grpo_evaluate.py:139-142` (`repeats_to_compare` then
`read_summary(repeat.summary)`), and `loop.py:598-604` (`part_baseline`: `exists()` then `read_summary`).

**Scenario.**
- With the baseline runs concurrent, slot k's first run can read `..._repeat1/summary.json` in the window between that
  job's `open(..., "w")` and its write.
- The read gets an empty or partial file and raises `JSONDecodeError`, with the same consequence as #1: a failed job and
  a stopped loop.
- Unlike #1, a restart resolves it.
- The window is microseconds, so this is rare.

**Fix.** Write `summary.json` (and `comparison.json`) with `write_json_atomically`.

**Confidence.** High that the window exists; the probability is very low.

### 6. (Low) Repeats finishing together can be compared twice

**Where.** `evaluation.py:404-415` (`repeats_to_compare`) and `grpo_evaluate.py:138-143`.

**Scenario.**
- The first run and a repeat each write their summary, then each checks for the other's.
- If both summaries exist before either job checks, both jobs compare the pair.
- The result is two `comparison.json` writes with the same content, and two `fixed_targets` lines with a comparison
  for the same repeat, which doubles a point on the dashboard.

**Fix.** Let only one side compare, for example the first run whenever both are complete. Or create
`comparison.json` with `open(..., "x")` and skip on `FileExistsError`.

**Confidence.** High that it can happen; the impact is cosmetic.

### 7. (Low) The value-benchmark dashboard alert can fire for the current version from an older version's interval

**Where.** `src/lean_search/monitoring/alerts.py:224-240` (`worse_value_benchmark`).

**Scenario.**
- `latest()` skips None, so `upper`, `version` and `difference` can each come from a different line.
- Suppose v2's line had `against_reference.upper < 0`, and v4 is scored with `against_reference` None, for example
  because v0's kept scores are missing or the bootstrap is degenerate.
- Then `upper` is v2's negative value, `version` is 4, and the status shows v4, so the alert says "Value v4 ... worse
  than v0".
- The loop.log alert (`worse_than_reference`) is per trend and correct.

**Fix.** Read all three fields from the last line of the series (`trend.latest["fields"]`), not column by column.

**Confidence.** Medium on the mechanism; the trigger is rare.

### 8. (Low) `stop_idle_repls` from a waiting worker can stop more than the over-limit share

**Where.** `lean/pool.py:74-81` (`stop_idle_processes`).

**Scenario.**
- `running` includes the busy REPLs of over-limit workers still finishing their last search.
- To get down to `keep_running`, the pool therefore stops idle REPLs that the under-limit workers will reuse next.
- Those then restart and re-import the header on their next search.
- Nothing is wrong (replay is transparent and the counts are consistent); some header imports are wasted around each
  limit drop.

**Fix (optional).** Pass the number of searches the loop knows are in flight above the limit, or stop only
`len(idle) - (keep_running - busy_under_limit)`.

**Confidence.** High on the mechanism; the cost is small.

## Checked and found correct

- **REPL stopped while a search holds it.** `stop_idle_processes` skips `_busy`, which covers acquired REPLs and those
  restarting. `Queue.get` on a non-empty queue does not yield, so acquire plus `_busy.add` is atomic. The pool size
  equals the worker count, so no getter waits on an empty queue.
- **Concurrent stop calls.** `stop()` takes the REPL's lock, so concurrent `stop()` calls, or a `stop()` alongside a
  search's request, are serialized. A stopped REPL restarts and replays on its next use.
- **Memory reads on dying processes.** `memory_usage()` runs synchronously next to the `running` check, and
  `read_memory_usage` tolerates zombies.
- **progress.json.** It is written with `write_json_atomically` (tmp file, then `os.replace`), so no half-written read.
- **Stale progress.json.**
  - It sits in a per-version directory.
  - A same-version re-run (restart) reads the earlier attempt's count, which equals the new job's count until the new
    job reports.
  - Before the job reports, the limit counts the whole concurrency. That is conservative.
- **The limit after an evaluation ends.** Workers re-check when the task ends, whether by success, failure or
  cancellation (`asyncio.wait` on the task). `running_evaluations` and `SubprocessEvaluations.running` are cleaned in
  `finally` blocks with no await between the job's exit and the removal, so there is no transient drop to the floor.
- **Cutting off at the pause.** `watch` cancels and then waits until the task is done, and `run_logged`'s `finally`
  awaits `stop_job` (SIGTERM, then SIGKILL, then `wait`). The servers therefore never sleep under a live job.
  - `finish_evaluations_beside_sampling` does not turn the cancellation into a failure.
  - A cut-off kind stays unmarked and is due again after the pause, through the schedule or the request file.
- **Concurrent baseline jobs.** Directories, `.log` files and `children/evaluations/<dir>/evaluation.pid` are separate
  per run. `run_logged`'s earlier-job check looks only in the run's own record directory. `**/*.pid` at session start
  covers the evaluations. The `repeats_to_compare` glob ignores the `.log` files. `MetricsWriter` appends one write per
  line.
- **Old files.**
  - Old `phases.jsonl` lines (no `beside_sampling`) parse, and this is tested.
  - Old status lines lack `evaluation_failures`; the alert reads that as 0.
- **Value alert with no v0 score.** `against_reference` None leads to no alert, in the loop and on the dashboard (apart
  from #7).
- **Config validation.** It range-checks the floor only with `beside_sampling`, and the shipped configs parse.

## Blockers for running on the node within 2 hours

1. **Finding 1 must be fixed before `init`/`run`**, for `loop.toml` and for the smoke cycle alike.
   - Otherwise there is a ~2/3 chance the start crashes in version 0's probe baseline, and once it does, no restart gets
     past it.
   - The minimal fix: `probe_slot_directory` considers only directories with a `summary.json`, plus a test.
2. **Finding 4, if the loop directory already exists on the node**: remove the incomplete `*_v0000*` evaluation
   directories, or use a fresh loop name. Nothing is needed for a fresh `init`.
3. **Not a blocker, but decide before the first long run:**
   - #2 (stop the evaluation pool's idle REPLs in its tail, or accept ~165 REPLs and watch the host memory);
   - #3 (probe `max_wall_seconds` against the 30 min pause wait).
