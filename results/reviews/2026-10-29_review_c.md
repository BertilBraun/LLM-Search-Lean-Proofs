# Review C: search-tree GRPO, design and implementation (2026-10-29)

Scope: DESIGN.md from "Next phase: search-tree GRPO" to "Known issues", and the code listed in the brief (master at
14c3164). Read-only. I ran the pure-Python tests (`tests/rl`, `tests/graph` without Lean, parts of `tests/search` and
`tests/lean`: 492 tests, all pass except one flaky test, see T5) and four scratch scripts in this directory against the
real code and the visible student's 244 old-format trees: `tree_stats.py`, `group_shapes.py`, `duplicate_problem.py`,
`parse_speed.py`. Anything I could not check against code or data is marked **unverified**.

## Executive summary

**Verdict.** The harness, labelling and trainer are carefully built and mostly correct. I found no off-by-one in the
mapping from tactic spans to tokens, no masking error, and no temperature mismatch. The PPO bookkeeping is sound. The
reward scheme is defensible for a learning project. A measurable improvement within about $200 is plausible but not
assured. The main risks are elsewhere:

- **Throughput and scheduling.** About 60% of the rented GPU time would be idle.
- **Measurement validity.** The probe is likely limited by wall-clock time, there is no noise floor, the value gate is
  driven by noise, and the overfit report is biased.
- **One real data bug** that corrupts the overfit test.

Fix the top five before renting (each is an hour or less of code). Then run the node checks in T1 before starting the
loop.

**Top 5 issues**

1. **[blocker for the overfit test, major overall] Expansion texts are looked up by `(problem_name, node_id)`, so two
   trees of the same problem in one phase swap their texts** (`rl/policy_data.py:194`). The overfit config re-feeds
   each of 300 statements as soon as its last search finishes, with 112 concurrent searches, so this happens all the
   time. Verified with the real `build_policy_data` (`duplicate_problem.py`): the failing block "oops" is trained at
   +0.5 and the proof "win" at −0.5. The overfit report also measures the wrong thing (D9).
2. **[major] The loop leaves most GPU time idle.** GPU 0 only trains, so it is idle while sampling. All searches pause
   while it trains, so GPUs 1–3 are idle during training (`rl/loop.py:471–519`, `loop.toml:68`).
   - My estimate for one phase of about 4–5k sequences × ~650 tokens: ~1–1.5 h of training against 15–30 min of
     sampling. That gives ~35–45% average GPU use, and the pause does not even buy on-policy data (item 3).
   - Fix: keep sampling during training (one version stale, which already happens anyway), and serve on GPU 0 while
     sampling. Sleeping a server on the training GPU is already implemented.
3. **[major] Off-policy data is invisible to PPO.** Searches span several phases: an unsolved 64-expansion search takes
   about an hour at ~1 expansion/min per search.
   - The "old" log-probabilities are the trainer's own weights at phase start (`rl/policy_trainer.py:358`). Samples drawn
     by versions k−1, k−2, … therefore get a ratio of 1 and pass the clip unchecked.
   - The version is recorded only per tree, at finish (`rl/tree_store.py:31`), so staleness cannot even be measured, and
     the sampler-agreement metric mixes it with numerical mismatch.
   - Fix: record the policy version per `ExpansionTexts`. Report staleness. Either drop samples more than 1–2 versions
     old, or use the recorded vLLM log-probabilities as behaviour probabilities with a truncated importance weight.
4. **[major] The value gate is a coin flip, and the gate benchmark is skewed.**
   - Noise: the headline metric rests on ~50 proof-vs-expanded pairs (DESIGN, "Benchmark and gate"), so its standard
     error is ~0.07. The pass threshold is +0.01, and the gate runs every phase (`loop.toml:74`, `value_every_phases =
     1`). A model no better than v0 passes in roughly 40–45% of attempts, so μ = 0.15 switches on within a few phases on
     noise.
   - Skew: the benchmark search is log-probability best-first. Visible-reasoning samples have a median cumulative
     log-probability of −76 (p10 −192, measured on the 244 trees), against a fixed −2.8 for automation steps
     (`gate_search.toml:61–63`). Every automation chain is therefore expanded before any policy child, and the
     benchmark's labelled states are dominated by sweep-produced states.
5. **[major] The fixed targets may not measure what they claim.**
   - (a) The probe's 10-minute cap per problem probably binds before 16 expansions (96 concurrent searches at
     ~100 expansions/min is ~1 expansion/min per search). The probe then measures solves per wall-clock time, which
     moves with explanation length and server load. **Unverified**: check the stop reasons of the first probe.
   - (b) There is no noise floor. Version 0 is probed once, at T = 0.8, so "beyond noise" is undefined. Run the v0 probe
     twice.
   - (c) MATH-500 retention is not in the loop at all; DESIGN says "per phase".
   - (d) The probe runs with whatever value model is published. Once a value model passes the (noisy) gate, probe changes
     mix policy and value.

## 1. Design

**D1 [major] Will it improve the policy measurably?** Plausibly, at small budgets. The signal is concentrated where
the policy already succeeds:

- On the 244 old trees, the median first proof is at expansion 1. Only 14 of 171 solved trees needed 8 or more
  expansions (`tree_stats.py`).
- 1,761 of ~2,050 group samples have no proof-graph tactic; 162 have exactly one (`group_shapes.py`).

So GRPO here is mostly "raise the probability of the root-level proofs the search already finds, push down failures at
those nodes", i.e. expert iteration with negatives. That should improve 16-expansion probe success on easy and medium
problems by a few points, which is about the noise level of a 501-problem probe (paired standard error ~1.5–2 pp when
10–15% of problems are discordant).

To make a positive result detectable:

- fix item 2 (roughly twice the data for the same money);
- measure the noise floor (item 5b);
- report per stratum and first-expansion success, where the effect should show first.

**D2 [minor] Per-tactic credit is mostly moot here.** Explanation tokens (mean ~120) get the sequence-level score
either way and outnumber tactic tokens. The median proof is 1–2 tactics. 71 of 124 first-expansion proofs are a single
tactic.

- The per-tactic vs sequence comparison in the single-step test will very likely be inconclusive: 512 states × 8
  samples, clustered by state, give a standard error of ~1.5 pp, and the expected difference is smaller than that.
- Treat that test as a smoke test that success rises on trained states, not as a credit comparison.

**D3 [minor–major] A no-op beats a failure.** DESIGN says "a no-op never beats a genuine attempt", but no-progress
gives R = −0.075 and a failure gives R = −0.15. In a group without a positive sample, no-op and redundant tactics get
a positive advantage.

- Measured with the real code on the old trees: 19 no-progress and 7 redundant-hypothesis tactics with positive
  advantage. 11 of 166 groups with signal have no proof-graph tactic at all. This happens when the sweep proved the
  node and every policy sample failed or made no progress.
- Small now, but it is a reward-hacking direction RL can amplify ("rising no-progress share" is already on the
  dashboard).
- Fix: drop groups whose known samples all have G = 0, i.e. require at least one proof-graph (or, after the gate,
  off-graph with q > 0) sample. Or set no-progress L = failure L.
- Also, the docstring of `rl/single_step.py:10–11` ("its failing and no-progress samples go below the baseline of its
  unknown ones") contradicts the code: unknown samples are outside the baseline (`rl/advantages.py:69`).

**D4 [minor–major] Censoring and ε turn "explored once" into negative reward.** An expanded off-graph state gets R = 0,
which is below the baseline (b ≈ 0.2–0.5 at proof-graph nodes), even after a single expansion
(`search/tactic_labels.py:152`, `rl/grpo_groups.py:101`). A never-expanded sibling is neutral.

- ε-exploration (0.1 of picks) and the value model's ordering therefore decide which siblings get penalised.
- A sibling expanded once just before the proof was found elsewhere is pushed down. Its never-expanded twin is not.
- Value targets weight off-graph nodes by n/(n+4); the policy reward does not.
- Fix: treat off-graph states with fewer than ~2–3 expanded nodes in their subtree as unknown for the policy, or scale
  their R by the same n/(n+4).

**D5 [minor] Ordering bias in the baseline.** Unknown samples (often reasonable progress) are left out of the baseline,
so b is computed only from proofs, failures and no-ops. That inflates negatives. It is an accepted simplification, but
it should be stated in the write-up.

**D6 [major] Value-model loop.**

- The gate's statistics are covered in item 4.
- Every phase trains a value model from the *published* one on that phase's trees alone (`rl/loop.py:259–262`). A
  rejected model's training is discarded, so before the first pass no model ever sees more than ~1 phase of data, and
  the first accepted one is chosen by noise.
- The guards DESIGN lists are partly off in config: `value_replay = ""` (`loop.toml:82`, "10% v0 replay") and
  `retrain_from_base = false`.
- Value training plus the gate add ~20 min per phase to the pause (estimate).
- Recommend:
  - gate every 3–4 phases, on the accumulated trees of those phases;
  - require the gain to exceed ~2 standard errors from a paired bootstrap over trees;
  - make the A/B search (DESIGN's "decisive test") the real switch for μ;
  - consider leaving μ at 0 for the whole run given the budget.

**D7 [major] The gate benchmark search is not representative** (item 4). Use a value-free priority that treats policy
and sweep comparably, for example one of:

- the block-token log-probability, summed or averaged over the Lean block only (computable from the recorded tokens);
- depth plus number of goals;
- a random-priority search.

Check the benchmark's composition: the proof-over-expanded pair count and the share of automation-made states.

**D8 [major] Starting-policy A/B lacks the obvious control.** The naming A/B compares two fine-tunes on the
*rewritten* data (numbered vs named). Nothing checks that the rewrite itself does not hurt search: chunks of k ∈ {1, 3,
5, 7, rest} push towards long blocks, and DESIGN measured ~80% failure for 9+ line blocks.

- Add visible student v2 as a third arm of the probe comparison. That costs one probe (~1 h); v2 already exists.
- The A/B is also selected on the probe set, which is then the RL target. The winner's-curse bias deflates the measured
  RL gain slightly. Use the gate set or another held-out slice for the A/B.

**D9 [major] The overfit test's report is biased** (`experiments/grpo_loop.py:185–198`; `rl/statement_sources.py:139–
154`).

- Solve rate per phase is computed over *trees*. A statement is re-fed as soon as its previous search finished, so easy
  statements, which finish in minutes, contribute many trees per phase and hard ones fewer than one.
- The curve then moves with search speed and mix, not just policy quality, and a phase also holds trees from searches
  started under older versions.
- Fix: rounds (each statement once per round, round = phase, searched with one version), or a per-statement solve rate
  of searches *started* under the version.
- Together with item 1, the overfit test as configured cannot show what it is meant to show.

**D10 [minor] Over-engineering relative to the budget.** μ / value pseudo-labels, the gate every phase, per-tactic
credit and search-time renaming each add surface but little expected effect at this scale. My order, if time runs
short:

- keep: proof-graph groups, the harvest, the harness fixes;
- make optional: the value loop (μ = 0 throughout) and the naming A/B (default to numbered names, which carry no
  renaming risk).

**D11 [minor] Replay is the same 384 examples every phase.** `chosen(..., f"{config.seed}/lean")` uses a constant
seed (`rl/training_phase.py:132–147`), and `phase_config_text` only changes `policy.optimization.seed`
(`rl/loop.py:258`).

- Over ~60–100 phases with 8 replay sequences × ~100 steps per phase, each of the 256 Lean and 128 math examples is
  seen ~2× per phase, i.e. hundreds of times in total.
- The replay NLL is then memorised and stops regularising toward the SFT distribution.
- Fix: seed with the phase number.

**D12 [minor] Pool supply (unverified).**

- The curriculum feeds each *verified* pool v3 statement once per loop and never repeats.
- `results/phase6_pool_v3/README.md` shows only a 1,600-statement verification sample; its "Verified for the
  curriculum" table is empty. `grpo_loop.sh` does not start the verifier.
- At ~16 s of Lean per verification, and the loop consuming maybe 200–400 statements/h, check that
  `expert_iteration/pool_v3/verified.jsonl` on the node holds tens of thousands of statements spread over the
  difficulty bands before starting, or run the verifier alongside.

**D13 [minor] Design text vs measurement.**

- "Every group has at least one sample on the proof graph" is false when the sweep proved the node (11/166 groups
  above). Harmless, since such groups are mostly dropped, but D3 is the consequence.
- "Held-out states and MATH-500 per phase" is implemented as every 6 h without MATH-500 (item 5c).
- DESIGN's reward bullet still describes "potential-based value shaping h(parent) − h(child)" in L
  (DESIGN.md:506–507). The code has no shaping: `rl/grpo_groups.py:96–109` gives L = closing bonus only, and the rl
  README table agrees with the code. Delete the sentence, or it will end up in the write-up.

## 2. Implementation bugs and risks

**I1 [blocker for the overfit test, major] Text collision across trees of the same problem** (item 1).
`texts_by_node = {(expansion.problem_name, expansion.node_id): …}` (`rl/policy_data.py:194`). Edge ids are per tree, so
`completion.edge_id in sample.edge_ids` (`:211`) then matches another tree's completions. The advantages stay with the
first tree's labels.

- Fix: build the policy data per record (`record.expansions` together with that record's groups), or key by
  `(tree index, node_id)`.
- Add a test with two trees of one problem.
- Curriculum runs are unaffected only because a statement is never fed twice. Any future replay or repeat would
  reintroduce the bug.

**I2 [major] Staleness is not recorded** (item 3). `ExpansionTexts` has temperature and top_p but no policy version.
`TreeEntry.policy_version` is read at tree completion (`rl/loop.py:431`).

**I3 [major, node] RAM with paused searches plus an evaluation pool** (unverified, but cheap to check). During the
pause, 112 paused REPLs keep their proof states (threshold restarts at 2 GiB private memory or 8,000 states). The
probe starts 96 more REPLs and miniF2F 120 more (`loop.toml:63/111/119`). On top of that come six vLLM processes and the
loop process.

- At 0.5–1 GiB average per REPL this is 100–230 GiB on a ~128 GB node, and an OOM kill during an evaluation also takes
  down the paused searches.
- Fix: before evaluating, restart idle paused REPLs above ~0.5 GiB. Or run evaluations with lower concurrency. Or
  evaluate through the loop's own pool after cancelling the paused searches. Watch the first probe.

**I4 [major] The probe's wall cap** (item 5a): `[evaluation.probe] max_wall_seconds = 600`, `concurrency = 96`.

- Fix: set the wall cap to ≥ 3,600 s so that expansions are the budget.
- Log per-problem stop reasons in the summary (`WALL_CLOCK_BUDGET` share).

**I5 [minor] The renamed-statement check uses the plain proof.** `verify_against_original(..., result.proof)`
(`rl/renaming.py:107–109`) verifies `state.proof` without the heartbeat wrappers. `verify_state` uses
`executed_proof` precisely because the plain text can behave differently (`try` around a step that hit its limit).

- Such proofs are counted unsolved and their trees discarded, including their value targets.
- Fix: verify the wrapped text (the wrapper is available in verification), and record `plain_verified`.

**I6 [minor] Harmless trailing no-ops are penalised in proof samples.** No-ops skipped after a nested proof closed
(`try …`, `skip`, `done`) repeat the closing state (`lean/repl.py:528`). They are therefore labelled `no_progress`
(`search/tactic_labels.py:146`) and get −0.075 − b inside successful samples. This is documented, but `done` after a
closed nested proof is good style, not a no-op the model should unlearn. Suggest masking them instead.

**I7 [minor] Mislabelled failure after an open nested proof.** When a flattened nested proof ends with its goal open
and outer tactics follow (`lean/plans.py:358`, `Stop(UNSOLVED…, applied_until=position + 1)`), the *next outer* tactic
becomes `failing`. The fault lies with the nested proof's last tactic or its `have`, which Lean would blame. The effect
is small; noted for the error-tier statistics.

**I8 [minor] Inaccessible-name matching of intermediate states** (unverified frequency). Intermediate tactic states
match nodes through the node's own (renamed) key or the pre-`rename_i` *last* state of edges into it
(`search/graph_labels.py:220–229`). An intermediate state printed with a different `✝` numbering than every edge into
that node stays `unknown` and does not split onto the proof graph. This undercounts proof-graph tactics; it does not
mislabel them.

**I9 [minor] `edge_tactics` falls back silently.** When a failure occurs after all executed tactics applied (should not
happen), `count = applied + 1` makes `len(spans) != len(tactics)` and the whole sample silently falls back to sequence
credit (`rl/token_credit.py:109`). Count these fallbacks in `PolicyDataMetrics` next to `token_mismatch_sequences`, so
a harness change that shifts spans cannot go unnoticed.

**I10 [minor] Duplicate work and memory per phase.** The trainer and the loop both parse and label every tree of the
phase (`rl/loop.py:537–553`, `experiments/grpo_phase.py:67`), including unsolved trees whose token records feed nothing
in the policy part.

- Measured typed-parse cost: ~0.36 s per 64-expansion tree with tokens (`parse_speed.py`). Fine for hundreds of trees,
  but the Python objects for ~500 trees run to several GiB per process.
- Optional: drop the token records of unsolved trees at write time, or keep the texts in a separate file per tree.

**I11 [minor] The overfit config shares the main gate path.** `loop_overfit.toml` sets `value_benchmark` but
`value_every_phases = 0`. That is fine as is. Note that in the overfit run the policy servers swap to adapters trained
on corrupted data (I1).

Checked and found correct (to save the next reader time):

- `decoded_offsets` multi-byte handling;
- the inserted opening and token-less closing fence, including the position shift past the removed span;
- explanation / tactic / gap / closing assignment;
- a flattened `have` opener's span covers `:= by`;
- repeats of sweep tactics by the policy (spans via the automation edge);
- unparsed samples merged into one failing sample but trained one sequence per completion;
- PPO clip flags and pessimistic bound;
- the k3 KL;
- old log-probabilities computed once, before the first update, and reused in pass 2;
- LoRA dropout 0 (no train/eval mismatch);
- prefix-cache reset after weight swaps (`policy/server_control.py:58,96`);
- restart in each stage (publish skipped if `current.json` already has the phase's version; evaluations resumable per
  version);
- probe/gate/curriculum disjointness by name (pool v3 is grouped by canonical statement and excludes traced
  statements, so the 512 validation states are not in the curriculum);
- harvest and ε are off in every evaluation (`rl/search_models.py:53–63`).

## 3. Testing and node checks

**T1. Run on the node first, before the loop (in this order, each minutes to an hour):**

1. `grpo_loop.sh check`, then **score the check samples with the trainer** (packed and unpacked, `compile_layers` on)
   and compare with the vLLM log-probabilities at T = 0.8. Today's tests use a tiny Qwen2 without packing or compile
   (`tests/graph/tiny_models.py:45`). The production path (Qwen3.5 hybrid layers via `fla`, `packed_hidden_states`,
   torch.compile, `--logprobs-mode processed_logprobs` semantics) is only checked after a full first phase. Pass
   criterion: mean |Δ| ≲ 0.05 nats, no position-dependent drift inside packed rows.
2. **A dry-run phase on real trees**: run `grpo_phase.py` on the gate-search trees (they are solved trees with groups)
   to measure training seconds per sequence, peak memory and agreement. This decides passes and phase size *before*
   the loop runs, and confirms the estimate behind item 2.
3. The heartbeat replay (already planned).
4. RAM: 112 searches running, then pause and start a probe-sized pool; watch RSS (I3).
5. One probe of v0 at the configured settings: wall time, stop reasons (I4), then **a second v0 probe** for the noise
   floor (5b).
6. Pool supply (D12) and tokenizer files in `grpo_start/merged` (the trainer loads its tokenizer from there,
   `experiments/grpo_phase.py:78`).
7. One in-place publish plus a request: check that a sample's recorded log-probability changes and the prefix cache
   was reset. The publisher was tested on the old node with adapters; this checks it with merged weights.

**T2. Missing tests that matter:**

- (a) two trees of one problem in one phase (I1);
- (b) a trainer test with packing on (CPU can't run fla; at least packed vs unpacked on the tiny Qwen2 if
  `packed_hidden_states` supports it);
- (c) labelling of the trailing no-op and the open-nested-proof cases (I6, I7) as explicit tests, so the choices are
  deliberate;
- (d) `report` on a fixed list with a statement searched twice (D9).

**T3. Real behaviour is tested where it matters most.** Harness, flattening and per-tactic states are tested with Lean
(`tests/lean/test_harness_lean.py`, `tests/search/test_search_with_lean.py`, `tests/graph/test_grpo_with_lean.py`).
Labels, advantages, token credit and policy data have direct unit tests, and the loop runs with fakes plus real Lean
for start-state and renamed searches. What is not tested anywhere off the node is vLLM itself: token ids, processed
log-probabilities, `/pause`, `reload_weights`, sleep and wake.

**T4. The cheap tests de-risk mostly the right things, with gaps.**

- Single-step: good as a smoke test of the whole data → trainer → servers path and of "success rises on trained
  states". Weak as a credit comparison (D2).
- Overfit: the right idea, invalid as configured (I1, D9).
- Naming A/B: add the v2 arm (D8).
- Missing: a cheap test that the loop beats *doing nothing on the same compute*, e.g. the probe of v0 twice (noise) and
  of the version after ~5 phases. Without that, "improves beyond noise" has no reference.

**T5 [minor] Flaky test.** `tests/rl/test_loop.py::test_a_restart_finishes_the_interrupted_training` fails in ~1 of 3
full-suite runs with `[1, 1, 2] == [1, 1]`: the fake loop sometimes starts phase 2 before `run_until` stops. It passes
alone. This is a race in the test helper, not a production bug, but it will cause false alarms.
