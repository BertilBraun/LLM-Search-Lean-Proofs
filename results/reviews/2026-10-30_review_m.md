# Review M (design): search options against the loop's Lean errors and the held-out harness (commit 028ede5)

Scope: `git show 028ede5`. I read it against DESIGN.md ("Policy update: GRPO over sibling groups", "Fixed targets",
"Search options against the loop's errors") and `src/lean_search/rl/README.md`, and against the code around it:
`rl/single_step.py`, `rl/fixed_targets.py`, `rl/search_models.py`, `search/search.py`, `policy/expander.py`,
`policy/prompts.py`, `rl/grpo_groups.py`, `rl/policy_data.py`, `expert_iteration/loop_search.py` and
`experiments/configs/grpo/search/visible_student_v2.toml` (the loop's template). I did not run anything.

The short answer to question 1 is **no, not as built**. The harness pairs every variant with the baseline on pooled
per-sample success. That is the right statistic for neither the feedback round nor temperature. It also cannot
resolve the expected effects of `tried_context` and name repair at 512 states. Most of this is fixed by analysis
choices and two small control variants, not new machinery. Question 3 has a hidden trap: enabling any option in the
loop also changes what the loop's own evaluations measure, including its alert and rollback signal (issue 5).

## Findings, by severity

### 1. (High) Feedback is judged on pooled per-sample success, which penalizes it by construction

**Where.** `rl/search_variants.py:370-420` (`pooled_rate`, `paired_comparison`). `comparison_table` shows only the
pooled difference.

**Problem.**
- Feedback adds 4 samples only at states where the first round did badly. The pooled rate is
  `successes / samples` over all states, so these extra samples drag it down even when they rescue states.
  - Illustration with assumed numbers: 44% first-round success, feedback on 30% of states, 15% success in the
    feedback round.
  - Pooled success: (8 · 0.44 + 0.3 · 4 · 0.15) / (8 + 1.2) = 0.402.
  - The table would show about −4 points, with a CI below zero, for an option that only added successes.
- A feedback sample reaching the same reference state as a first-round sample counts as a success. In the tree it is a
  `DUPLICATE` edge and adds nothing to the search.

**The fair comparisons.** The sub-questions about the fair comparison resolve as follows:
- *First round vs total, within the same run*: this is the exact counterfactual for "feedback off". The first round
  is drawn from the same prompt at the same temperature as the baseline. So the gain is total minus first round on
  the same states, with no between-run noise. It is **not** a fair comparison of value, though: more samples can never
  hurt.
- *Baseline with 12 samples*: unfair the other way. It spends the extra samples on every state, not just the
  triggered ones, and dilutes like the pooled rate.
- *The right control*: the same trigger and the same 4 extra samples with the **original prompt** (blind
  resampling). That isolates what the error text adds. If blind ≈ feedback, adaptive blind resampling wins outright:
  - it keeps the same prompt, so the extra samples join the node's existing GRPO group (8 + 4) with a better baseline;
  - there is no new prompt distribution;
  - nothing new has to be trained on.
- *Per token*: normalize by generated tokens. Feedback prompts are longer (two blocks and errors, up to ~1,400
  characters), but the system prompt and goals are a cached prefix, so prompt tokens matter little.

**Recommendation.**
- Add `feedback.show_attempts = false` (blind control: same trigger, original prompt, still marked `feedback` for
  accounting). Alternatively, an in-run "dual" measurement mode that requests both rounds at each trigger and judges
  each against the first round only. That gives exact pairing on the same triggered states and the most power.
- Report per **state**, not per sample:
  - **rescued states**: no successful first-round sample, but a successful feedback sample;
  - **distinct new states** and **distinct new successful states** the round added (dedup against the first round);
  - both per 1k generated tokens.
- Show the paired CI on these metrics, plus `first_round_success_rate` against the baseline as a free A/A check.
- Choose `min_children` from data instead of fixing it at 2. For the measurement run, set `min_children` above 8, so
  the round fires whenever any sample failed. Then stratify by the first round's child count (0, 1, 2, 3+): one run
  gives the marginal yield per token at every threshold.

### 2. (High) The headline metric is pass@1 against a reference proof, which rewards mode-seeking and ignores breadth

**Where.** `single_step.root_samples`. A sample succeeds only by closing the goal or reaching **the reference proof's**
next or later state.

**Problem.**
- Best-first search uses an expansion through its distinct children: does at least one lie on *a* proof, and how many
  live options does it add.
- Per-sample success is pass@1 on one fixed route. A valid alternative route counts as failure, and duplicates count
  as extra successes.
- This biases the comparison:
  - **toward lower temperature**: more mass on the modal (often the reference) step and more duplicate successes;
  - **against the feedback round**: "Give a different tactic" pushes off the modal route.

**Temperature at 1 expansion.** It can be measured fairly enough at one expansion with the right metrics. Nodes are
expanded once, so the breadth of one expansion is exactly what the search gets from that node. But per-sample success
is the wrong metric for it.

**Recommendation.** The primary metrics should be:
- **pass@n per state**: `states_with_success`, already computed but not paired or bootstrapped;
- **distinct successful children**;
- **distinct children**;
- **distinct candidates per expansion** (after text merging);
- each per generated token.

Keep per-sample success and valid rate as secondary health numbers. Optionally, score the new children with the value
servers (expected remaining steps relative to the node) as a route-agnostic usefulness proxy. It carries the value
model's own bias, so treat it as supporting evidence only. Add `temperature = 1.0` to the sweep, so the direction of
the curve is visible and not only its lower half.

### 3. (High) `tried_context` is confounded by running the sweep first, and its loop cost cannot be seen here

**Where.** `single_step_run_config` (`single_step.py:114-130`): the sweep runs only when
`failed_automation_in_prompt` is set.

**Problem.**
- The variant differs from the policy-alone baseline in two ways: the prompt line, and the sweep having run first.
- The sweep's children pre-empt the policy's. A policy sample reaching the same state as `field_simp` or `constructor`
  becomes `DUPLICATE`, so `children` and the new-state share drop for reasons unrelated to the prompt. Success is
  unaffected, but issue 2 makes children the metric that matters.
- The 120 s per-state cap now includes the sweep: 7 tactics at 200k heartbeats with a 60 s emergency stop each.
  On slow states the policy's candidates never run (`_run_batch` checks the wall clock per candidate), so the
  variant silently drops the hardest states from its denominator. `paired_comparison` still pairs them, with 0
  samples against 8.
- **Held-out bias.** Yes, the held-out setup biases this option, through the sweep-first confound and the state cap
  above. The prompt-line comparison itself is fine once the control below exists.
- **Ceiling.** Bare `linarith`/`nlinarith`/`positivity` samples are 9.4% of failures, about 2.9% of samples. The
  loop's sweep contains only `nlinarith` of these three. The line can therefore name `nlinarith`, but never
  `linarith` (implied by a failed `nlinarith`) or `positivity`. Even a perfect line moves well under 3% of samples.
- **Cost in the loop.** The option requires `overlap = false`. Every loop expansion then waits for the whole sweep
  before its policy request. With 112 searches in flight this costs throughput only if REPLs or memory, not GPUs, are
  the binding limit. The harness's `wall_seconds_ratio` (per-state latency, beside a loaded loop) cannot tell which.

**Recommendation.**
- Add a `sweep_first` variant (automation_then_policy, no overlap, no line). Pair `tried_context` with it, not with
  the policy-alone baseline.
- Count and exclude states where either arm has fewer policy samples than requested, or raise the cap for both.
- If the line survives, write "linarith, nlinarith" when `nlinarith` failed, and consider adding `positivity` to the
  sweep. It costs milliseconds and covers the rest of the 9.4%.
- Only an in-loop measurement (expansions per REPL-hour, GPU utilization) can show the price of `overlap = false`.

### 4. (High) Power: 512 states × 8 samples resolves about ±1.5-2 points, and two options sit below that

**Rough numbers.** These are estimates; one A/A run will measure them.
- **Per-sample success.** The per-state variance of a rate from 8 samples, with heterogeneous states, is about
  p(1−p)/8 ≈ 0.12/8. For a difference between two runs that is ≈ 0.03 per state.
- Over 512 states this gives a standard error ≈ 0.8 points, so a 95% CI of about ±1.5 points. pass@8 per state is
  similar or a little worse.
- **Name repair.** On the loop's mix, unknown identifiers are 5% of the 31% errors ≈ 1.5% of samples ≈ 64 of 4,096.
  Dotted, repairable at 0.85 and then valid is perhaps a third of that, about 20 samples, or 0.5 points at most.
  No between-run comparison can see it.
- **`tried_context`.** Its ceiling is well under 3% of samples (issue 3), so a realistic effect is around 1 point.
- **Shared baseline.** One baseline run is shared by six comparisons at 95%. An unlucky baseline makes every variant
  look better at once, and about 0.3 false positives are expected anyway.
- **Distribution.** The 512 held-out states are traced steps of reference proofs. The 31% error mix was measured on the
  loop's own nodes, which are policy-made states, often odder and harder. The held-out mix may differ.

**Recommendation.**
- Measure name repair **within run** (successes with and without the repaired samples; the code already records
  `repaired_successes`), and above all **offline** (issue 9). Not as a variant against the baseline.
- Run the baseline twice. The loop's own held-out evaluation at the same pause is a free second baseline on the same
  version and config: copy its trees.
- Treat a variant as a winner only if it clears the A/A spread and a Holm-corrected interval.
- Before anything else, print the baseline's error table next to the loop's 34k-sample mix. If they differ much, the
  held-out states are the wrong place to tune error-targeted options.

### 5. (High) Enabling an option in the loop silently redefines the loop's evaluations, including the rollback signal

**Where.**
- `fixed_targets.evaluate_held_out_states` builds the held-out run config from the loop's search template:
  `single_step_run_config(evaluation_run_config(template, target))`.
- `sample_success` counts every root sample in the denominator.
- The probe and miniF2F use the same template.

**Problem.**
- **Feedback on.** The held-out per-sample success falls mechanically by about 9% (the arithmetic of issue 1). The
  alert is at `min_held_out_success_fraction = 0.9` of version 0's.
- **`failed_automation_in_prompt` on.** The held-out evaluation starts running the sweep first.
- **Temperature changed.** Every held-out and probe number shifts.
- **The probe trend.** The dashboard draws each probe slot against version 0's two runs. After the switch, that trend
  measures "policy + option" against "policy without option", and the option's effect is booked as learning.

**Recommendation.** Pin a separate **evaluation template**: the current one, all options off, by default the loop's
template as it was at version 0.
- The held-out states, the probe and miniF2F keep measuring the policy and value on an unchanged search.
- An option's effect on search is measured by the A/B in the run plan, not by the trend.
- If an "as deployed" probe is also wanted, run it as an extra, labelled series.
- Policy health metrics computed from the loop's trees (`tree_summary.valid_blocks`, distinct samples per expansion,
  cut-off share) should count first-round samples only, or the alerts calibrated on the early phases shift as well.

### 6. (Medium-high) Masking repaired samples removes the negative signal against hallucinated names

**Where.** `grpo_groups.policy_groups` (`:236`) drops samples whose executed edge was repaired. `search._apply`
overwrites the first run's result (`:650-660`).

**Problem.**
- The sampled text did fail. Masking it means the policy is never told, so with repair on, the pressure against
  hallucinated names falls.
- If the repaired edge was the node's only policy sample reaching the proof graph, `require_policy_proof` drops the
  whole group. The other 7 samples' signal is lost too.

**Recommendation.**
- Record the pre-repair failure on the edge: its failure and the index of the failing tactic. Train the **sampled**
  text with what it would have done:
  - the tactics before the bad name keep their rewards;
  - the tactic with the bad name gets the failure (−0.15);
  - the rest is masked.
- This is exactly on-policy. Keep the repaired edge for the search only.
- A later option is a small SFT-style term on the repaired text (it was never sampled, so there is no behaviour
  log-probability for the PPO ratio). Not now.

### 7. (Medium) In the loop, the feedback round fires after a proof and its tokens are charged to the solve

**Where.** `PolicyExpander.expand` (`expander.py:243-262`) together with `_Expansion.stopped`, `_run_batches` and
`_ledgers` in `search/search.py`.

**Problem.**
- With harvesting on (the loop), `finish_after_proof` keeps the expansion going after its proof. The expander is then
  asked for the next batch.
- The proving expansion often has fewer than 2 policy children, so a 4-sample feedback round is requested at a node
  that is already closed.
- `_ledgers` charges it to `solved_at` ("costs settled after the proving step were incurred before it"). Here that is
  false: the feedback request is sent after the proof.
- The `combined` harness variant has the same pattern, through `tried_context`'s harvest setting.

**Recommendation.**
- Skip the round when the expansion proved its node, or more generally when the node is closed.
- Separately, the trigger counts only *policy* children. At a node where the sweep made 3 children, the round fires
  anyway. Decide whether that is intended; the stratified run in issue 1 can tell.

### 8. (Medium) Feedback and GRPO: the separate groups are correct; group size and data share need watching

The design itself is sound:
- A feedback group is drawn from, and trained on, its own prompt with recorded log-probabilities. That is on-policy;
  there are no off-policy prompts in training.
- A separate group is right, because GRPO's baseline must be per prompt.
- Feedback samples do not bias the first-round group's advantages or the reward definition. They change the tree
  (new children, possibly a different proof graph), which is the intended effect.

Points to watch:
- **Group size.** Groups of 4, fewer after merging identical texts, give a noisy mean baseline. When all 4 fail
  there is no signal at all. Consider `sample_count = 8` for the round if the measurement favours feedback; it costs
  only at triggered nodes.
- **Selection and weight.** Feedback groups come only from nodes where the first round did badly, a hard-node skew.
  They add a second group at the same node, which doubles that node's weight in a per-group loss. Put the feedback
  groups' share of trained groups, and of summed |advantage|, on the dashboard.
- **Lost negatives.** At a node where only a feedback sample reached the proof graph, the first-round group has no
  policy proof and is dropped. Its 8 failures are never penalized. This is consistent with the `require_policy_proof`
  rule, but it is a lost opportunity.
- **The bigger payoff, later.** Distil feedback successes into the *first* prompt (an SFT or RFT term on the feedback
  sample's text under the original prompt; there is no valid PPO ratio). That is how an error-feedback round makes
  the base policy better instead of only patching the search. Not before feedback is shown to help.

### 9. (Medium) Name repair: 0.85 mostly catches renames; calibrate offline instead of on the held-out states

**Measured difflib ratios** (last component):

| Category | Name pair | Ratio |
|---|---|---|
| Catches | `div_le_iff → div_le_iff₀` | 0.95 |
| Catches | `pow_le_pow_left → …₀` | 0.97 |
| Catches | `two_mul → two_mul'` | 0.93 |
| Catches | `lt_of_pow_lt_pow → …_left` | 0.87 |
| Misses | `sum_Iio_succ → sum_range_succ` | 0.69 |
| Misses | `pow_lt_pow → pow_lt_pow_left` | 0.80 |
| Misses | `mod_two_eq_zero_or_one → mod_two_eq_zero_iff` | 0.78 |
| Misses | `add_pow_two → add_sq` | 0.47 |
| Wrong meaning, passes 0.85 | `add_le_add_left → add_lt_add_left` | 0.93 |
| Wrong meaning, passes 0.85 | `sum_le_sum → sum_lt_sum` | 0.90 |
| Wrong meaning, passes 0.85 | `cast_sum → cast_sub` | 0.88 |

So 0.85 is mostly a Mathlib-deprecation fixer.

**Precision matters little.** Lean checks every repair, so a wrong repair costs one Lean run and at worst yields a
valid but unintended step, which is fine for search. Recall and Lean time are what matter.

**Recommendation.**
- **Calibrate offline, with no GPU:** take the dotted names among the phase 2-3 trees' unknown-identifier failures (~530 of the
  34k samples).
- Replay the repaired blocks in Lean for:
  - thresholds 0.6, 0.7, 0.8 and 0.85;
  - the top 1 or 3 candidates per name.
- Measure the repaired-valid rate and the added Lean seconds.
- Add a deprecation alias table (old name → new name from Mathlib's `@[deprecated]` history up to the pinned commit).
  It has no false positives and probably carries most of the gain.
- Component-level matching (`Iio ↔ range`, `pow_two ↔ sq`) or name retrieval would catch `sum_Iio_succ`. That is not
  worth building at a ceiling of about 1.5% of samples.
- Enable repair if the replay shows it is cheap. That needs no harness variant, but it does need issue 6 fixed first.

### 10. (Medium) Prompt wording

**Feedback round.**
- "Give a different tactic or tactics that avoid these errors" discourages *fixing* a close attempt. Many of the
  measured errors are one edit from working:
  - `rw` pattern not found → `rw [← h]`;
  - `linarith failed` → add a hint term;
  - a missing ₀ in a name.
- Suggested wording: "Write a new tactic block for this state. If an attempt was close, fix it; otherwise try another
  approach."
- **Error text.** For `linarith`, `unsolved goals` and similar errors, Lean's message is mostly a dump of the goal the
  prompt already shows. At 300 characters, that dump crowds out the useful part.
  - Keep the first line.
  - For type mismatches, keep the "has type … but is expected to have type" lines.
  - For `rw`, keep the pattern.
  - Drop the context dump.
  - Say which tactic of the block failed (the executed prefix length is known).
- **Duplicates.** Samples that reached existing states (15%) are never shown. If all 8 reached the same state, there
  is no round at all, although diversity is exactly what is missing. Consider one line: "These reached a state already
  seen: …".

**`tried_context`.**
- At most nodes nearly all 7 sweep tactics fail, so the line is close to constant and carries little information.
- "simp_all failed" invites over-generalizing to all `simp` calls. Suggested wording: "These tactics alone fail here:
  …".

### 11. (Medium) Temperature: do not change the training sampler's temperature on this evidence

The loop's samples are both search and RL exploration.
- Lowering T raises pass@1 and cuts breadth (issue 2). It also makes more groups identical in reward, so fewer groups
  carry signal, and it concentrates entropy that RL needs.
- Decide temperature for the **loop** only from search-level, per-token evidence (the A/B in the run plan) with the
  trainable-group yield in view.
- A lower temperature that helps pass@n per token can be used for evaluation and final proving runs without touching
  training.
- `min_p` (e.g. 0.05) is the usual cheaper way to cut tail tokens (syntax, invented names) while keeping breadth. Under
  RL it changes the behaviour policy, though: the trainer's recorded log-probabilities would have to be the truncated
  distribution's. That makes it a separate decision, not a drop-in.

### 12. (Low-medium) Harness execution details

- **Variant order.** Variants run one after another. Loop load beside sampling and the risk of a version change both
  vary over the run, so later variants differ systematically, and a version change leaves early variants complete and
  later ones empty. Interleave instead: per chunk of e.g. 64 states, run every variant. A version change then leaves
  balanced partial results.
- **Cost columns.** `wall_seconds_ratio` beside a loaded loop is not a cost. Use generated tokens, prompt tokens and
  Lean seconds. Report wall time only as a latency check.
- **Coupled sampling.** A per-request seed derived from the state (if the client and vLLM accept `seed`) couples the
  temperature variants' samples and cuts the paired variance cheaply.
- **Re-runs.** The loop is learning: RL already gives −0.15 to failing tactics on proof-graph nodes, so error shares
  should fall by themselves. Re-run the baseline and the chosen option every few versions.

## Question 4: cheaper or better alternatives

1. **Let RL do it, and check first.** Plot the error-category shares per phase (every phase so far). Unknown names,
   syntax and bare automation are exactly what the local −1 penalizes. If they already fall, the options target a
   shrinking problem.
2. **The deferred "malformed sample" negative.** DESIGN lists Lean-checked syntax and unknown-name failures from *any*
   tree (not just proof-graph nodes) as a small separate negative. It attacks 11% of the errors (syntax and unknown
   identifier) at no sampling cost and fixes the cause, not the symptom. It is likely better value than name repair.
3. **Adaptive blind resampling** (issue 1). If the error text adds nothing, sample 4 more with the same prompt and put
   them in the same group. That is simpler for GRPO and has no prompt shift.
4. **Hinted automation.** `linarith failed` is the largest category (29%). A sweep entry like `nlinarith [sq_nonneg
   (a - b), …]` with hints generated from the goal's variables and hypotheses, applied only to polynomial-inequality
   goals over ordered fields, is CPU-only. It may close many of the goals the policy keeps failing on.
5. **Gate extra compute by value.** Fire the feedback round only at nodes whose value estimate is in the frontier's
   top-k. That puts the extra tokens where a proof is likely.

## Verdict

The options are implemented carefully: opt-in, recorded on the edges and texts, and kept apart in GRPO. The harness
is the right idea. But as built, its headline comparison:
- would show feedback as harmful;
- would favour lower temperatures for the wrong reason;
- cannot separate `tried_context` from the sweep running first;
- has no power for name repair.

None of it measures "search per unit of compute": a single expansion against a reference route can only screen. The
decisive test is cheap: an A/B **inside the loop**. The loop is search-bound anyway, so it costs no extra compute and
measures solves per generated token on the real distribution. That is the test of "search per compute"; the harness
only screens for it. Fix issues 5-7 before any option goes into the loop.

### Run plan

**Stage 0: free, from existing trees, no GPU.**
- (a) Error shares per phase, every phase so far.
- (b) The share of expansions with fewer than 1, 2 or 3 policy children and at least one failure: the trigger rate
  and the extra-token estimate.
- (c) The name-repair Lean replay of issue 9 (the dotted share of ~530 unknown-identifier failures): repaired-valid rate and Lean seconds per threshold
  and k.
- (d) The held-out baseline's error mix (from the loop's latest held-out evaluation trees) against the loop's mix.

**Stage 1: harness screen.** All 512 held-out states, one served version, variants interleaved per 64-state chunk.
About 9 held-out-evaluation equivalents of sampling.

| Variant | What | Paired with |
|---|---|---|
| baseline | as now | the A/A pair |
| baseline_2 | the loop's own held-out run at the same pause (copy its trees), or a second run | baseline |
| feedback_always | `min_children = 9`, attempts shown, 4 samples | within run (first round); feedback_blind |
| feedback_blind | same trigger, original prompt (new `show_attempts = false`) | within run; feedback_always |
| sweep_first | automation_then_policy, no overlap, no line (new flag) | baseline |
| tried_context | as now | sweep_first |
| temperature_0.6 / 0.7 / 1.0 | as now, plus 1.0 | baseline |
| name_repair | within run in feedback_always/blind (with and without repaired samples), not as its own variant | — |

Metrics, paired and bootstrapped:
- pass@n per state, distinct children, distinct successful children and distinct candidates, each per 1k generated
  tokens;
- for feedback: rescued states and the added distinct (successful) states per stratum of first-round children;
- per-sample success and valid rate as secondary.
- Exclude states with missing samples, and Holm-correct.

What would justify moving on to Stage 2:

| Option | Moves on to Stage 2 when |
|---|---|
| Feedback | Its rescued states and added distinct successful states per token beat feedback_blind with a paired CI above 0, in the strata it would trigger on. Set `min_children` where its marginal yield per token is at least the first round's (expected: 0-1 child). If blind ≈ feedback, take adaptive blind resampling instead. |
| `tried_context` | Distinct children (and pass@n not lower) beat sweep_first by more than the A/A spread, and bare-automation failures fall clearly. Otherwise drop it: its ceiling is small and it forces `overlap = false`. |
| Temperature | Report the curve. Change only evaluation and final-proving temperature on Stage 1 alone. The loop's training temperature needs Stage 2 and the trainable-group yield. |
| Name repair | Enable directly on Stage 0(c) if the repaired-valid rate is at least ~30% of attempts and Lean time rises less than 1%, after issue 6 is fixed. |

**Stage 2: in-loop A/B.** One option at a time. Prerequisites: evaluations on the pinned template (issue 5) and the
fixes to issues 6 and 7.
- Assign each problem to an arm by a hash of its name, 50/50, for 2 phases. Both arms share the policy versions, the
  time and the load.
- Compare per arm:
  - solve rate;
  - generated tokens per search and per solve;
  - expansions and Lean seconds per search;
  - wall seconds per search (for `overlap = false`);
  - trainable proof-graph groups per search (the loop's actual product).
- **Enable** the option if the solve rate per generated token (or solves at the arm-matched token budget, from
  `solved_at`) is higher with an interval excluding 0, with no loss of trainable groups per GPU-hour.
- Then re-run Stage 1's baseline on later versions occasionally, to see whether RL has made the option redundant.

Do **not** roll out one option per phase without an A/B. The phase-to-phase change in policy, curriculum and noise is
larger than any of these effects, so the attribution would be guesswork.
