## Blocker

### B1. A merge done on a rank other than 0 has no weights: in every value phase on 4 GPUs, the value model is served and published without weights. Verified.

`training/resident.py:249` → `policy/adapters.py:145-159` (`write_premerged` → `model.save_pretrained`), called from
`rl/resident_trainer.py:272-282` (`index % world_size == rank`: the value merge runs on rank 1). The per-phase path
has the same problem: `rl/training_phase.py:339-345` (`merge_on_gpus` → `premerge_adapter` → `write_premerged`).

transformers 5.17.0 (the locked version) writes checkpoint shards only on torch.distributed rank 0:
`PreTrainedModel.save_pretrained` → `DistributedMixin.should_save_on_this_rank` returns
`is_main_process and get_rank() == 0` whenever a process group is initialized. On rank 1 it writes `config.json` and
`generation_config.json` but no `model.safetensors`. `write_premerged` then writes `premerged.json` into the directory
and renames it into place, so the directory looks complete.

- Failure scenario: `loop.toml` with `gpus = [0, 1, 2, 3]`, `persistent = true`, phase 4 (the first value phase).
  Rank 1 hands off `handoff/<hash>/` with the marker and no weights. `handed_off_version` accepts it, and the value
  servers' `restore_gpu`/`reload_weights` load a directory without weights. In the best case this fails and the loop
  stops. Every restart then re-serves the same handoff, whose marker is still there, so the loop stays stuck until
  someone deletes `/dev/shm/lean_search/<loop>/handoff`. With `persistent = false`, `merging.merge` moves the weightless
  `<adapter>/../merged` into `weights/v<k>/value` and the version is recorded before it is served, so `current.json`
  points at it and every restart fails at `servers.serve(current)`. Before this range the per-phase path reached this
  code only when the gate accepted a value model. Now it reaches it in every value phase.
- Reproduction: `test_review_h_ranks.py` runs `TrainerRank.train` on two gloo ranks on the CPU (policy and value
  phase, twice). The single-rank handoffs each hold `model.safetensors`. In the two-rank run both value handoffs
  (`899123e038aa6f71/`, `9879e749455eec03/`) hold only `config.json`, `generation_config.json` and `premerged.json`.
- Fix: write the merged state dict without transformers' rank gating, e.g.
  `huggingface_hub.save_torch_state_dict(state_dict, temporary)` (sharding and shared tensors handled) plus
  `config.save_pretrained`/`generation_config.save_pretrained`. Or run every merge on the main rank, at the cost of a
  slower value-phase merge. In `write_premerged`, assert that a weights file exists before writing the marker. Add a
  two-rank gloo test of `TrainerRank.train` and `merge_on_gpus` that checks the handoff/premerged weights. Today every
  resident and merge test is single-rank, which is why this was not caught.

## Major

### M1. A stop or crash between recording the version and clearing host memory leaves the handoff (up to ~14 GB of tmpfs) for another phase. Verified.

`rl/loop.py:1130-1142` (`record_durably`) and `rl/loop.py:1102` (`publish` skips the handoff once `current.trigger`
is this phase's).

- Failure scenario: an operator runs `grpo_loop.sh stop` during the ~1-minute durable write after an early resume
  (very likely right after watching a phase finish), or the loop crashes in that window.
  1. Cancelling `finish_phase` cancels the `record_durably` task. Its `asyncio.to_thread(publish_phase, ...)` thread
     keeps running and records the version, but `prune_adapters` and `shutil.rmtree(self.handoff_root)` never run.
  2. On restart the stage is PUBLISHING and `current.trigger == "phase k"`, so `publish` takes the non-handoff branch
     and nothing clears `handoff/`.
  3. It stays until the next phase's `record_durably`. At that phase's handoff, tmpfs holds parked (~14 GB) + the
     stale handoff (9.4-14 GB) + the new handoff (9.4-14 GB). The README's sampling budget is already at the limit
     with one handoff (109 of 109 GiB), so this risks the OOM killer on the 128 GB node.
- Reproduction: `test_review_h_loop.py::test_a_crash_after_the_record_leaves_the_handoff_behind`. After the restart
  closes phase 1, `handoff/` still holds `00782306da31c292` and `e82596840337b2c5`.
- Fix: in `publish`, when `current.trigger == phase_trigger(phase)` (already recorded), clear `handoff_root` (and run
  `prune_adapters`). Or, more simply, clear `handoff_root` in `finish_phase` once the stage reaches EVALUATING.
  Optionally shield the record-and-clear sequence from cancellation (`asyncio.shield`, and await it in `run`'s
  `finally`).

## Minor

### m1. The README's "ranks stop by themselves within a second once the loop's process is gone" holds only between commands. Plausible.

`rl/resident_trainer.py:198`.

- Failure scenario: the loop is SIGKILLed during a `train` (minutes) or during a first `prepare` (model building,
  1-2 minutes). The ranks finish the command and leave GPU memory allocated meanwhile. The restarted loop refuses to
  start ("Jobs of an earlier loop still run") until they do. This is safe but contradicts the docs.
- Fix: correct the README, or check `loop_process.alive()` from a watchdog thread that calls `os._exit`.

### m2. The parked weights stay in `/dev/shm` after the loop stops. Plausible.

`training/resident.py:81-106`.

- Failure scenario: the loop stops (health stop, end of run, crash without restart). `parked/policy.bin` and
  `value.bin` (~14 GB) are never removed. That host memory is then missing for manual `grpo_evaluate.py` runs or a
  next loop with another name.
- Fix: unlink `parked/` in `PersistentTrainer.close()` after the job has stopped, and say so in the README.

### m3. The "Value model worse than v0" alert outlives the value model it is about. Plausible.

`monitoring/alerts.py:206` (`worse_value_model`).

- Failure scenario: the published value model v4 is flagged worse. Phase 8 publishes value v8. The dashboard keeps
  showing the v4 alert (the latest `value_arm` row) until v8's first value arm runs, which is up to two slots (~4 h)
  later.
- Fix: alert only when the row's `published_value_version` equals the current published value version (the
  `value_training` and `value_benchmark` families carry it).

### m4. Resuming a run started before this range silently weakens the trigger and the hard stop. Plausible; only if such a run is resumed.

`rl/tree_store.py:37` (`summary` defaults to an empty `TreeSummary`) and `rl/evaluation.py` (`valid_samples`
defaults to 0).

- Failure scenario 1: index entries written before the change count 0 trainable groups. A phase in flight then waits
  until `max_sampling_minutes`, or never triggers if all its trees are old.
- Failure scenario 2: a version-0 held-out `summary.json` written before the change has `valid_samples = 0`. Then
  `stop_held_out_valid_rate` and `min_held_out_valid_rate` are 0, and the hard stop can never fire.
- Fix: refuse to run such a run, or recompute missing summaries and the version-0 held-out rate on start. At minimum,
  log when version 0's `valid_samples` is 0 while `samples > 0`.

### m5. `write_phase_config` rewrites `training/phase_<k>.toml` in place (`write_text`) while ranks may be reading it. Plausible; very unlikely in practice.

`rl/loop_services.py` (`write_phase_config`).

- Failure scenario: `prepare` and `train` of a phase write the same path. A rank reading it at the instant it is
  truncated parses an empty config, crashes, and the phase is trained once more.
- Fix: `write_json_atomically`-style temporary file and rename (or a per-command file name).

## Checked and found correct

- The resident trainer is bit-identical to the per-phase job at one and at two ranks. In `test_review_h_ranks2.py`,
  one policy phase: resident_1 == per_phase_1 and resident_2 == per_phase_2 exactly.
- The second and third resident phases compile 0 graphs (18, 0, 0), as the README states. The test only asserts the
  third.
- Rank divergence on `prepare`/`train`: a rank that misses a `prepare` runs the same `ensure_models` collectives inside
  `train`, so the collective sequence matches.
- `TrainerChannel` atomicity and sequence handling, and job restart and `TrainerDiedError` handling.
- Park/unpark: tied parameters are deduplicated, merges stay in the unparked copy, and the mapping is never written.
- The early-resume ordering, with the version recorded before the evaluations and before the benchmark scoring.
- The Clopper-Pearson/McNemar arithmetic, the pair-statistic bootstrap, the late-solve quarter, and
  `last_good_version` retention.

Unrelated to this range, but seen while checking: one rank and two ranks differ by ~1e-2 (absolute, on LoRA weights)
after one multi-step phase at lr 1e-2, in the per-phase data-parallel path too. The existing test checks a single
step only. It is probably Adam amplifying float-order noise on near-zero gradients, but "a step on two ranks equals
the one-process step" should not be read as "a phase does".
