# Search shape and policy prior at equal generations

Full miniF2F-valid, SFT v2 policy and value v0 as merged models (two vLLM instances per GPU), 120 searches pinned to
40 CPUs (`deployment/background.sh`), overlap and early value scoring, the 7-tactic sweep. Priority
f = 0.25·depth + h + w_p·(mean negative step log-probability on the path; automation steps −2.8). About 1,024 policy
generations per theorem: n = 16 × 64 expansions, n = 8 × 128, n = 4 × 256. Per-theorem wall budget raised to 3,600 s
(it stopped 2–6 searches per run, all unsolved hard theorems). Configs `experiments/configs/phase3_search_shape_*.toml`;

## Findings

- **Shapes are within noise at the full budget** (156 / 154 / 153; n8 vs n16: 2 newly solved, 4 lost; n4 vs n16: 4 / 7).
  Against row 4 every run loses a few more than it gains (n16: +4 / −5, n8: +5 / −8, n4: +5 / −9), also within noise.
- **Smaller n is better at small generation budgets, larger n at the end**: solved within 32 / 128 / 1,024 generations
  is 117 / 143 / 156 for n16, 130 / 146 / 154 for n8, 132 / 141 / 153 for n4. At equal Lean seconds per theorem n8
  matches n16 up to 120 s (136 vs 127 at 10 s), n4 trails throughout.
- **Lean is the cost of small n**: every expansion runs the automation sweep and value scoring, so Lean per policy
  sample rises from 0.74 s (n16) to 0.85 s (n8) and 1.05 s (n4), and at the same 43 cores the GPUs get fewer samples
  per second (busy phase: 129 / 106 / 74 samples/s). Small n also runs out of frontier more often (4 / 11 / 34
  searches). Busy-phase GPU utilization stays ~92% for all shapes (value prefill fills the gap).
- **Whole runs took ~61 min each, not 12**: with the wall budget no longer binding, 10–15 hard theorems (IMO/AIME,
  candidates timing out at 20–40 Lean-seconds per expansion) run on alone for up to an hour while the GPUs idle
  (whole-run utilization 26–41%). Busy-phase throughput is unchanged from the GPU-utilization study.
- **Policy prior (at n = 16): no gain** — 156 / 154 / 153 for w_p = 0 / 0.2 / 0.4 (0.2 vs 0: +3 / −5; 0.4 vs 0:
  +2 / −5); the anytime curves overlap. Inconclusive, leaning against a prior.

## Recommendation for the expert-iteration loop

- **n**: n = 16 is best at the full ~1,024-generation budget and cheapest in Lean per sample; n = 8 is as good at
  ≤ 256 generations per statement and slightly better at small budgets. The owner chose n = 8, which these numbers
  support for the loop's short first stages; keep stage budgets of ≥ 128 expansions so n = 8 spends ~1,024 generations
  on statements that reach the last stage. Avoid n = 4 (more Lean per sample, frontier exhaustion).
- **w_p**: inconclusive, so the default 0.2 (per the orchestrator's rule); nothing here shows the prior helping, and
  w_p = 0 did as well or better, so 0 is an equally defensible choice. It was swept at n = 16, not at n = 8.
- **Wall budgets**: cap the hard-theorem tail (e.g. 600–1,200 s, or a Lean-seconds budget) rather than 3,600 s; the tail
  produced 0–2 proofs per run while idling both GPUs for ~45 minutes.
